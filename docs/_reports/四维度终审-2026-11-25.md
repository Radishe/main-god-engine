> 四个独立审查 agent 各守一维：整体结构一致性 / 实现精细度 / 产品设计符合度 / 对抗钻空子。

## 1. 致命层（开工前必须修）

### P0-1 裁判面没有任何写保护 —— 整个门禁建立在「裁判可信」这个未验证假设上

- **证据**：无 CODEOWNERS、无 git hooks（实测 Glob）；`gates/check.py:235-246` 的 `write_path_overlaps` 只打印不阻止；分片 `agent_can_edit_shard:false` / `shard_owner` 只是字符串，无 enforcer；真实验收测试在 `gates/tests/`，不在任何包的 writable 内，也没被保护。
- **后果**：实现 agent 改 `gates/tests/s1-g2-02.py` 打印 PASS，或改 `check.py` 让 `ready` 恒真，没有代码会拒绝。
- **修法**：外部机制（CODEOWNERS + branch protection + CI 路径白名单硬失败），**不要靠 check.py 检查自己**。

### P0-2 CI 允许「测试全红也能合入」

- **证据**：`.github/workflows/gates.yml` 只有三个 step：coverage（结构统计）、`--package P4`（`continue-on-error`）、`--invariants`（`continue-on-error`）。**没有一步执行 `--run` 或 X01~X05。**
- **注意**：简单去掉 `continue-on-error` 只会让 CI 永久卡红（I6 恒 PENDING、`--package` 默认不跑测试），并制造「把 I6 改成 PASS 了事」的坏激励。必须一并让 runner 变真。
- **修法**：新增 blocking 步骤跑 `--stage s1 --run` / `--stage sc --run` / `--stage si --run` / `--package <P> --run`；coverage 降级为信息报告；I6 用显式豁免+期限处理。

### P0-3 结算契约把玩法核心挤掉了（产品维度）

- **证据**：设定要求 D12「先算分值→达成率→定级→系数」、主神拥有汇率与评级定价权（`README.md:40-53`、`03-评分与评价体系.md`、`06-物品与公证体系.md:34-37`）。实现里 `settlement.json` 把 `credit_delta: integer` 定为清单必填，`ledger.py:72-73,91` 直接加总，`src/` 检索 `score/grade/coefficient` 零命中。
- **后果**：副本申报的是最终兑换点，主神不算分、不定级、不折算——`settle()` 退化成加法器。S3 想补评分链时，得改被 I4 冻结的字段集。
- **修法**：在 stub 增加 `claims` 结构化扩展字段（分值/体量/主线支线份额/事件标记）+ 版本演进规则，主神侧按 config 算分定级再折算 credits。**这是「游戏」和「防作弊加法器」的分界线。**

## 2. 高危层

### P1-1 `aborted` 完全绕过引擎计算

- **复现实测**：`completion=aborted, credit_delta=500 → credits 1500`；`-500 → 500`。`failure` 分支安全，但 `ledger.py:72-73` 只把 `failure` 交给引擎，`aborted` 走实例自报。
- **冲突**：D16 把死亡映射为「退出并按未完成结算」，而 aborted 正是未完成的一种；C11/D14 的「执行者永远是引擎」没覆盖它。
- **修法**：`completion != "success"` 统一交引擎计算，不采用实例 delta；补 `aborted ±delta` 测试。

### P1-2 只读账本视图不是深冻结

- **证据**：`v["credits"]=0` 正确抛 `rejected_direct_write`；但 `v["ability_ids"].append("stolen")` 静默成功、`v._data["credits"]=999999` 静默成功（实测）。引擎本体因 deepcopy 不受损——隔离是对的，坏的只是 `deep-frozen` 承诺，而 S1-G2-01 只测顶层写入。
- **修法**：`__getitem__` 递归包装为不可变视图，禁止 `_data/_hooks` 外部访问；补嵌套容器写入测试。

### P1-3 X02 恒真 + X05 可伪造（交叉印证）

- X02 `x02-01.py:43` import 实现里从同一份 stub 读出的 `REQUIRED/TYPES` 再比对，改 stub 两边一起变；且从不调用 `settle()`，no-op 实现也能过。
- X05 `x05-01.py` 纯正则信文本，手写 5 行假日志即 PASS（实测）；`executor=instance` 那个变异案例改的是 config 字面量、被 C11-01 的配置断言杀死，不是行为断言。
- **修法**：X02 走公共入口 `Engine.settle()`、按 stub error_codes 断言、去 import 内部符号；X05 日志带源文件/测试文件哈希与 commit，变异目标必须是实现代码，runner 现场采集而非信日志自述。

### P1-4 S0 假 FAIL 与 C25 三份真源（整体维度）

- `S0-G1-01` 实测 `FAIL D14 missing fields: 被否决选项及理由`——D14 已拍板却判红，只因决议文档字段名 `被否决` 与契约不一致。同类 `s0-g1-02.py` 根本不存在。
- C25 抹杀语义在 `coverage.json`（note 说 PENDING）、`manifest.json`（sc/G2 active）、`c25-01.py`（docstring 说 A7 未定、main 却查已存在的 config）三处互斥；「A7 未定」已过时（D16 已关闭 A7）。
- **修法**：统一 D14 字段名并补 `s0-g1-02.py`；补拍 C25 一条决议后一次性统一四处真源。

## 3. 中危层

- **`gates.yml` 之外**：`run_tests` / X04 runner 强制 `returncode==0` 且 TEST 行唯一、ID 与预期一致；`expand_run_order` 对不认识的 id 报错而非静默丢弃（`C30-01 (golden path)` 曾因此被漏掉）。
- **分片可自删验收**：`P*.json` 的 `tests: []` 会让 `--package --run` 报 `RUN_EXIT: PASS`（实测）；`shared_tests` 在 run 模式完全不计。需 hash 固化分片 + 强制 own 非空且对齐 manifest。
- **`blocked_by` 空壳解锁**：`contains:## D14` 加一行空标题即 RESOLVED；`file_exists` 对 0 字节 JSON 也通过（实测）；P6 写 `{}` 即 STARTABLE。需结构化正文校验 + JSON 可解析校验。
- **`integration_job.json` 死声明**：`assemble_from`/`pass_rule`/`packages` 四个字段无人消费，X04 只读 `run_order`；`vocab/`、`content/instances/` 均不存在。要么真拼接，要么删字段。
- **数字过时**：00 文件仍写 `hard_tests=55` / `PASS=5 FAIL=22` 等历史值，实测已是 `71 / PASS=9 FAIL=18`；§13.9/13.10/13.11 同日给三个版本。
- **subprocess 无 timeout**：一个 `while True` 测试拖死 CI 与并行 agent——直接违背「不停摆」目标。变异脚本原地改源码靠 `finally` 恢复，进程被杀就留下变异态。

## 4. 产品节奏判断（最重要的一节）

产品维度的一句话评议：**缰绳确实编好了，而且比大多数项目结实；但现在场上只有缰绳，没有马。**

- `content/` 不存在、0 个可玩副本；`gates/tests/` 39 个测试文件、`docs/_reports/` 6 份审计报告、00 文件 795 行、`src/` 4 个文件。
- §13.9 → §13.10 → §13.11 三个连续里程碑全是门禁自审；`HANDOFF: READY` 在 11-12 就达成，之后又做了三轮门禁改造。00 §13.8 自己承认玩法治理层「阻塞成游戏」。
- 公道话：X02 抓到 frozen 漂移、X04 抓到桩注入，对并行防漂移有真实价值。**错在把门禁完备度当成项目进度。**

**下一步目标应从 `HANDOFF: READY` 换成 `C30-01 PASS`（第一个异构副本跑通）。**

三条元决议的产品优先级（产品维度判断，与「解除并行阻塞」的排序不同）：
1. **C25 抹杀语义** 最影响「能不能玩」——D1 三次抹杀是唯一终局，且它现在是实现阻塞（配置写了、代码没写）。半页纸可拍。
2. **C16 扭曲节点边界** 居中——D15 高级通道前提，但普通副本不需要，可推迟到首个异构副本跑通后。
3. **C15 场景标签** 最可推迟——03 §5 只有三个标签名、素材零规则内容；若只为解 P6，拍「先用占位枚举、规则后填」即可。

## 5. 建议的处置顺序

| 序 | 动作 | 理由 |
| :-- | :--- | :--- |
| 1 | 先做 P0-2 + P0-1：让 CI 跑真判定、给裁判面加外部写保护 | 否则后面所有修复都可能被一次越界提交抹掉 |
| 2 | 修 P1-1（aborted）+ P1-2（深冻结）+ P1-3（X02/X05 去恒真可伪造） | 这三条直接决定「agent 写出的代码能不能信」 |
| 3 | 清 P1-4 与中危层的机械问题（假 FAIL、真源统一、数字对齐、timeout） | 低成本、消除误导 |
| 4 | 补 `claims` 扩展口与 D12 评分链，拍 C25 | 把加法器变回游戏 |
| 5 | 派 P7 做 2 个异构副本，目标 `C30-01 PASS` | 第一次真正「做游戏」，之后按需回头补门禁 |

**总判定**：现在不该放手。门禁体系是**设计上自洽、执行上可绕过、产品上偏离**——三层问题叠在一起，多 agent 并行会同时暴露这三层。先修 1~2，再谈派活。

**本地端到端复核**（CI 三个 step 逐条跑）：coverage `HANDOFF: READY`；baseline `ALLOWED`；invariants `PASS=7 PENDING=1`（信息项）；全量与 `--stage si --run` 均 `DENIED`（实现未写，预期红）。
