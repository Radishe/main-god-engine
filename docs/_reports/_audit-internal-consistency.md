## 二、逐条详述

### F01 · 【跨章矛盾｜高】`permanent` 绑定与 07 章 C 类抵扣直接冲突

**涉及**
- `docs/06-物品与公证体系.md:64`
- `docs/设计决议记录.md:52-59`（D1 抵扣顺序表）
- `docs/07-惩罚与死亡机制.md:7`

**原文引用**
> `06:64`：| `permanent` | **永久绑定，不可交易、不可丢弃** | 传说级、剧情关键物品 |

> `D1:56-58`：
> | A | 兑换点 | 优先扣除 |
> | B | 属性点 | A 不足时以 B 弥补 |
> | **C** | **物品** | **A、B 均不足时以 C 弥补** |

> `07:7`：新设计锚定**任务体量**……抵扣顺序 A(兑换点)→B(属性点)→C(物品)，三次失败抹杀

**为什么是问题**
1. **语义直接对撞**：`permanent` 的定义是「不可丢弃」；C 类抵扣的定义是「把物品拿去弥补惩罚额」。若「惩罚扣除」被实现为一次 `remove_item()`，则它与 `permanent` 的字面定义冲突；若被实现为「不删除但暂时失效/封印」，则 D1 的「扣除和体量相等的东西」在设计意图上破产——玩家「花了钱但没损失」，惩罚的威慑被架空。**两条路都破坏一个已拍板的设计。**
2. **对照可证这是遗漏而非有意**：`06:66` 明确为 `droppable` 写了惩罚场景——「可丢失，**死亡或严重失败时概率掉落**」。也就是说 06 章作者**已经想到「惩罚会动物品」这件事**，却只给 `droppable` 写了这一路径，对 `permanent` 与 `tradable` 在惩罚下的行为**完全没有交代**。这不是「尚未数值化」，是**规则空缺**。
3. **后果不对称且反直觉**：传说级 / 剧情关键物品（`permanent`）恰恰是账面上价值最高的资产。若它们天然免疫 C 类抵扣，则「资产越贵越安全」，C 类的惩罚深度被玩家的资产结构反向操控——**与 D1 自己的立法意图（惩罚锚定体量，与玩家拥有什么无关）直接矛盾**。D1 废掉旧押金公式的理由之一正是「资产多的人相对风险反而更低」，而这里 C 类把同一个漏洞以另一种形式重新引入了。
4. **技术债里没有这一条**：T1~T13 讨论的是惩罚函数的**量**（多少），从未讨论惩罚对象的**可及性**（能不能扣）。两轮核验报告（v1/v2）只核「是否忠实转述素材」，也未触及规则交叉。

**建议**
- 在 06 章绑定类型表中新增一列「**惩罚可及性**」，明确三种类型在 A/B/C 抵扣下的行为（可扣 / 不可扣 / 可扣但转为封印）。
- 若决定 `permanent` 免疫 C 类，则必须在 D1 中写明**替代规则**（如：免疫部分转为额外 B 类属性点扣除，或计入一次失败计数），否则 C 类退化为「只吃便宜货」。
- 若决定 `permanent` 也可扣，则必须改写 `06:64` 的定义（「不可**主动**交易或丢弃」）并说明惩罚是主神发起的强制扣除，不属玩家主动行为。
- 无论选哪条，都需在 08 章 checklist 第 8 项旁补一句：绑定类型检查必须同时校验惩罚可及性。

### F02 · 【缺失机制｜高】属性点被扣后无恢复路径，且可能跌穿当前阶位

**涉及**
- `docs/设计决议记录.md:57`（B 类抵扣）
- `docs/05-玩家成长体系.md:13-18`、`:30-34`、`:80-81`、`:149-153`
- `docs/07-惩罚与死亡机制.md:38`、`:80`
- `docs/09-待确认细节.md:130-135`

**原文引用**
> `D1:57`：| B | 属性点 | A 不足时以 B 弥补 |

> `05:15-18`：| 一阶 | 20 |／| 二阶 | 40 |／| 三阶 | 60 |／| 十阶 | 200 |（技能/裸装属性上限）

> `05:30`：**主神对「裸装属性」设有硬性门槛。** ……**永久属性点的投放权必须握在主神手里**。

> `05:80`：| 一阶 ~ 二阶 | 永不触发永久死亡。即使进入高阶副本，死亡降级为「严重失败 + **高额扣点**」 |

> `05:149`：| **玩家阶位体系** | 仅能从「一阶 ~ 十阶」「新手」的旁证推断存在，**无玩家阶位与副本阶位的关系定义** |

**为什么是问题**（三个互锁的子问题，文档一处都没问）

**(a) 属性点不可再生**
`05:152`「属性获取途径：无素材」，`05:153`「兑换点与属性的换算：无素材」。同时 `05:30` 又明确「永久属性点的投放权必须握在主神手里」。两条合起来意味着：**永久属性点在本框架中是一种只减不增的资产**。而 D1 把它设为 B 类抵扣来源。结果是一次失败就造成**不可逆的成长倒退**——这不是「扣除和体量相等的东西」，这是把玩家的成长曲线当作消耗品。文档没有任何地方回答「被扣的属性点能否通过后续副本挣回来」。

**(b) 可能跌破阶位准入线，形成死亡螺旋**
05 章的表标题是「**玩家阶位** / 单项上限」。若该上限同时充当**阶位认定**依据（`05:150` 承认「'裸装属性门槛'」是晋升条件之一，只是数值未定），那么 B 类抵扣会同时做两件事：扣属性 + 可能把玩家打回低阶。叠加上一条（不可恢复），玩家一旦连败就**永久锁死在低阶**，而低阶又意味着准入的副本收益更低（`04:54` 收益衰减 ×0.8），形成**正反馈的死亡螺旋**。这是惩罚系统里最经典的失败模式，文档完全未设防。

**(c) 与 lethal 保护规则打架**
`07:80` 规定一阶~二阶「永不触发永久死亡。即使进入高阶副本，死亡降级为『严重失败 + **高额扣点**』」。若低阶玩家的兑换点不足，按 D1 就要走到 B 类扣属性。但低阶玩家的属性上限只有 20（一阶），**可扣额度极小**，很容易在几次失败内被扣穿到 0；而 `05:87`（抹杀后状态）写的是「一阶、属性**归零**」——也就是说「属性归零」在本框架里是**抹杀态的特征**。于是会出现一种荒诞状态：玩家没被抹杀，但属性状态与抹杀态无法区分。文档没有定义这两者如何区分。

**建议**
- 明确属性点的**再生规则**：是否允许用兑换点回购（则需补「兑换点↔属性」换算，正是 05 章缺口表里缺的那一行）、是否随晋升自动补足到阶位下限、或规定每个阶位周期内可回购次数。
- 明确**属性下限保护**：至少规定「B 类抵扣不得使任一项属性低于当前阶位的准入门槛」或「不得低于 1」。
- 明确属性点被扣后**是否影响已获得的阶位**。若影响，必须补「降阶」机制（见 F16）；若不影响，必须写明阶位认定不看当前属性值。
- 明确「属性归零但未被抹杀」这一中间态的存在与命名。

### F03 · 【悬空引用｜高】checklist 第 3 项 `can_modify_persistent_state` 从未定义

**涉及**：`docs/08-治理与审核.md:32`；全项目仅 3 处出现该字符串

**原文引用**
> `08:32`：3. `can_modify_persistent_state` 为 false。

**为什么是问题**
全库检索 `can_modify_persistent_state` 只有三处命中：08:32（checklist）、`设计决议记录.md:178`、`技术债与盲点.md:239`。后两处**都只是引用 checklist 第 3 项**，没有任何一处定义这个字段。具体悬空成三层：

1. **归属对象不明**：它是副本提交 JSON 里的一个**声明字段**（作者写 `false` 自证清白），还是审核时对**副本代码**做静态分析得出的**结论**？这两种解释的审核动作完全不同（读表格 vs 读代码）。
2. **两个来源互相否证**：`D9:171-178` 已拍板「副本 = 动态库，**可以带自有逻辑代码**」——一个能执行任意 C# 的 DLL，其 JSON 里写 `can_modify_persistent_state = false` **不构成任何保证**；而 `08:40` 又把第 11 项写成「静态扫描」。于是第 3 项（声明）与第 11 项（扫描）在同一张清单里承担了同一职责的两种互斥实现。
3. **没有 Schema**：`01:133` 把纪律表述为「`settle(副本结算清单)` 是唯一入口」，这个表述**根本不需要这个字段**。也就是说该字段是 checklist 单方面引入的，Schema 草案（`01:504-512`）里不存在。

**注意区分**：T6 讨论的是「**静态扫描这条防线强度够不够**」（隔离强度），**不是**「这个字段是什么」。这不是已自述缺口。

**建议**
- 在 01 章 §4.2 或新的 Schema 章节中正式定义该字段：类型（bool）、必填性、所在结构（副本元数据 / 清单头）、缺省值、以及「为 true 时的处置」。
- 若按 T6 的方案 B/C 走，应把第 3 项从「检查声明」改写为「**校验运行期隔离边界**」，并明确它不是 JSON 字段。

### F04 · 【悬空引用｜高】checklist 第 4 项「结算模板 ID」从未定义

**涉及**：`docs/08-治理与审核.md:33`

**原文引用**
> `08:33`：4. **结算模板 ID** 存在。

**为什么是问题**
「结算模板」这个概念**在整个文档集中零定义、零出现**（除这一行）。检索 `模板` 只命中：`01:507`「场景列表（引用框架的场景模板或资产 ID）」——那是**场景模板**，与结算无关；`01:397`「副本模板生成」——那是脚手架。

后果链条：
- 审核者要检查「ID 存在」，就必须有一个**可查询的模板注册表**。该注册表由谁维护、模板由谁编写、模板内容是什么（是不是 D12 那条「分值→达成率→定级→取系数」的公式参数化？）——全部空白。
- 更关键：`04:79` 已拍板「**晋升试炼**：……**该副本的结算规则由主神直接注入，副本作者无权修改**」。这句话**隐含了一个「结算规则可被注入」的机制**，也就是「结算模板」本应承担的东西。但 04 章和 08 章从未把这两件事连起来。**一个已拍板的核心机制（试炼副本直辖）依赖一个未定义的对象。**

**建议**
- 要么在 Schema 章节正式定义「结算模板」：模板 ID 命名空间、模板由 L0 维护、模板参数（哪些系数可被副本覆写、哪些被主神锁定），并明确晋升试炼 = 强制套用主神模板。
- 要么承认 checklist 第 4 项是**早期草案残留**，改写为「结算规则来源已声明（主神模板 / 副本自有）」，并补上它与 04:79 的对应关系。

### F05 · 【悬空引用｜中】checklist 第 2 项「合理的取值范围」无判别标准

**涉及**：`docs/08-治理与审核.md:31`；`docs/01-核心设计哲学.md:67`、`docs/README.md:37`

**原文引用**
> `08:31`：2. 每个属性轴有**合理的**取值范围声明。

> `01:67`：| **主神统一持有** | 属性的存储格式、更新方式、**边界规则（如数值范围 0–100）** |

**为什么是问题**
「合理」是一个判断词，而 `08:28` 与 `08:48` 两处都宣称 L1 的职责是「**只做二元判断**（允许/不允许）」。一个需要判断「合理」的条目**天然不是二元的**。同时 `01:67` 说范围由**主神统一持有**（举例 0–100），与「由副本**声明**范围」在权责上冲突：如果范围归主神，副本无需声明；如果副本声明，主神持有的「边界规则」是什么？

**建议**：把「合理的取值范围」改为机检项——如「每个属性轴必须声明 `[min, max]` 且 `min < max` 且区间落在主神允许的包络内」。把权责明确写清：**副本声明区间，主神限定包络**。

### F06 · 【悬空引用｜中】checklist 第 5 项的「基准分」无定义，且与 T4/T12 不连通

**涉及**：`docs/08-治理与审核.md:34`；`docs/03-评分与评价体系.md:123`；`docs/技术债与盲点.md:145-165`、`:384-399`

**原文引用**
> `08:34`：5. 理论最高总评分 ≥ **基准分** × 该阶位**最低比值**。

**为什么是问题**
03:123 已自述「无基准分定义、无比值数值」——**这一半是已自述缺口，不计入本报告**。但有一个**未自述的结构问题**：

T4 给出的「接通方案」是把 09 章的**阶位与评分区间表**（1000~2999 / 3000~5999 / 768000）当作体量标准，从而让 checklist 第 6 项（「推导出的副本阶位与任务分值设计匹配」）成立。但**第 5 项无法用这张表接通**：区间表约束的是「理论最高总评分必须**落在区间内**」（一个上下界），而第 5 项约束的是「理论最高总评分 ≥ 基准分 × 最低比值」（一个**下界**）。两者只有在「最低比值 = 1 且基准分 = 区间下限」时才重合。文档从未讨论这个等价性，T4 的 `:167-170`「待确认」两条也只问了「复用哪张表」，没问「第 5 项与第 6 项是否同一机制的两种写法」。

**结果**：即使 T4 被解决，checklist 第 5 项**依然无定义**，且可能与第 6 项给出**互相矛盾**的判定（第 5 项要求 ≥ X，第 6 项要求 ≤ 区间上限）。审核者遇到冲突时以哪条为准，无规定。

### F24 · 【缺失机制｜高】绑定类型是惩罚体系的唯一物品过滤条件，却无优先级规则

**涉及**：`docs/06-物品与公证体系.md:58-70`；`docs/设计决议记录.md:58`

**原文引用**
> `06:60`：三种绑定类型并存，在物品注册时**固定**，副本作者不能临时更改
> `06:64`：`permanent` —— **不可交易、不可丢弃**
> `06:66`：`droppable` —— 可丢失，**死亡或严重失败时概率掉落**
> `D1:58`：| C | 物品 | A、B 均不足时以 **C** 弥补 |
> D1 正文没有指定抵扣**顺序**（先扣哪件物品），也没有指定是否允许按稀有度排序、是否优先扣 `droppable`。

**为什么是问题**（这是 F01 的上位问题）

- `tradable`：无任何惩罚相关语义。

也就是说，**06 章的绑定类型事实上充当了惩罚系统的可及性过滤器**，但 06 章的设计意图（`06:64-68`）完全是**交易/掉落**语境，从未考虑惩罚。两个章节在概念上从未对接：06 章写绑定类型时不知道 D1 存在，D1 写 C 类时不知道绑定类型存在。

**后果**：即使 F01 被单独裁决（比如"permanent 也可扣"），仍然缺**抵扣算法**——是按 base_value 从低到高扣？按获取时间从新到旧扣？由玩家自选？玩家自选会导致"先扣垃圾"，使 C 类形同虚设（因为 `permanent`/高价值物品可被保留），这与 F01 论证的"资产结构反向操控惩罚深度"是同一个问题的第二个出口。

**建议**：这不是补一句注释能解决的，需要在 D1 中正式定义 **C 类抵扣算法**（候选集合、排序规则、玩家是否可干预、抵扣是否永久），并回头修订 06 章的绑定类型定义使其显式承担该职责。建议顺序：先定 F24 的算法，F01 的 permanent 处置自然落地。

## 四、我认为最严重的三个问题

### 第 1 名 · F01 + F24：`permanent` 绑定 × 07 章 C 类物品抵扣

**为什么最严重**：这是唯一一条**两个已拍板决议直接在语义上对撞**的问题，且**任何实现方案都会破坏其中一方**：
- 尊重 `permanent` 的「不可丢弃」→ C 类抵扣对高价值资产无效 → 惩罚深度被玩家资产结构反向操控 → **D1 废除旧押金公式的立法理由被自己的 C 类推翻**；
- 允许扣除 `permanent` → 06 章的核心定义被推翻，且「不可丢弃」对玩家的承诺（`06:70`「不存在『拿到手才发现不能交易』的意外」）失效。

而且这个问题**不在任何已记录清单上**：T1~T13 只讨论惩罚的"量"，两轮核验报告只讨论文档的"忠实度"，06 章与 07 章在概念上从未对接过——06 章写绑定类型时不知道 D1 存在，D1 起草时不知道绑定类型存在。**这是一个两章盲写产生的真实规则漏洞，不是数值待拟合。**

附带 F24 说明补一句注释不够：即便裁决了 `permanent` 的处置，C 类仍缺**抵扣算法**（候选集合、排序、玩家可否干预），而"玩家自选"会开出一个与 F01 同构的新漏洞。

### 第 2 名 · F02：属性点被扣后无恢复路径 + 可能跌穿阶位，形成不可逆的死亡螺旋

**为什么严重**：D1 的 B 类抵扣把**永久属性点**（`05:30`：投放权归主神，`05:152`：获取途径无素材 ⇒ 事实上只减不增）当作**消耗品**使用。三个后果互相放大：
1. 一次失败 = 永久成长倒退（不可再生）；
2. 反复失败 = 跌破阶位准入线（F16：降阶机制不存在）；
3. 低阶玩家（属性上限仅 20）会被更快扣穿，而 07:80 恰恰承诺他们"永不触发永久死亡"——**保护条款把他们推向了比死亡更难看的结局：属性归零，而 `05:87` 又把"属性归零"定义成抹杀态的特征。**

这不是"数值待拟合"，而是**惩罚体系缺少两个必需机制（属性再生、降阶）**，而文档把降阶误判为"素材缺口所以可以不做"（F16）。同时它阻塞了两项已判定为"倾向已定"的设计（感知门槛 F20、永久死亡保护 F14）。

### 第 3 名 · F03 + F04 + F09：08 章 checklist 有三项在检查不存在的东西，且"二元判断"定位不成立

**为什么严重**：08 章是唯一一份被标记为「**素材完整度：完整**」且被 README:87 描述为「D9 使第 3/11 条生效」的治理章节。但逐项回溯后：
- 第 3 项 `can_modify_persistent_state`：**全库无定义**，且与第 11 项（静态扫描）在同一张清单里承担同一职责的两种互斥实现；
- 第 4 项「结算模板 ID」：**全库零定义**，而 04:79 已拍板的"晋升试炼结算规则由主神注入"恰恰**依赖**这个未定义对象；
- 第 5/6/9/10 项：依赖基准分（无定义）、阶位推导（无算法）、风格标签匹配（语义判断）、魔改程度（无标准 + 无母本）；
- 而 `08:28/48` 宣称的"不需要理解玩法、只做二元判断"，与第 6/9/10 项的性质直接矛盾——`技术债:428` 只把这一项当作"好玩无解、属接受范围"关闭了，**没有意识到它是审核清单的分类错误**。

**根因**：08 章 checklist 是从脚本素材直接保留下来的早期草案，而它检查的对象（JSON 声明式副本）在 D9「副本 = 动态库」之后**已经变了**——文档只把第 3/11 条重新解释了一遍（T6），**没有对其余 9 项做过同样的回溯**。治理文档是"先建治理文档，再开 PR"（README:110）这条路线的前置，带着三个悬空检查项进入 Schema 设计，会直接污染 Schema 的字段设计。
