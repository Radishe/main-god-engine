## 2. 否决票与硬条件的原文摘要

### A 的否决（产品维度）

- 纪念标记「对能不能玩 ≈ 0、对多 agent 并行 ≈ 0，甚至为负」——它不进结算/评分/惩罚/准入任何运行链路。
- 拍 A 要在基线刚收紧到 PASS=11 的当口改 `states.json` + 测试 + 账本字段集，是纯回归风险。
- A 不是 P6 的阻塞项（P6 真阻塞是 `SCENE_RULES`）。
- **定性**：现在拍 A 就是终审批评的「补设定而非做游戏」。建议降级到 C30-01 之后。

### C 的否决（红队维度）

- `c30-01.py` 当前是硬编码 FAIL 占位；strict runner 只校验退出码 + 唯一 TEST 行，**不校验测试内容**。
- 棘轮对 `FAIL→PASS` 归为 `improved`，只打 note 不 DENIED —— 一个 3 行假测试 `print("TEST C30-01 PASS ..."); sys.exit(0)` 即可骗过。
- X04 结构性地无法识破 fake 替身冒充集成（它声明不重复实现 golden path）。
- `content/instances/` 非受保护路径，无需 gate-approved；CODEOWNERS 是占位符、标签可自贴。
- **最低转正条件**：C30-01 纳入 X05 式现场变异重放；必须有真实引擎调用证据（hook 计数 + 账本 SHA 只在两次 settle 处变化）；fake 不得通过集成门；P7 自身验收进 manifest 并 blocking。

### 三项共同的前置（红队，最高优先级）

1. `.github/CODEOWNERS` 的 `@REPLACE_WITH_MAINTAINER_TEAM` 必须替换为真实团队并启用 branch protection；`gate-approved` 不得由实现者自贴。
2. 裁判面改动（gates/、config/、决议记录、.github/，含 `--write-baseline` / `--write-package-hashes` / 测试断言 / mutation recipe）须独立维护者 review。
3. 棘轮的反向漏洞必须补：非绿转绿的测试须带可重放证据，否则拒绝写入 baseline。

### B 的硬条件（设定 + 红队 + 产品，三维度一致）

- `credit_delta` 必须在所有 completion 下停止作为 credits 来源；双字段共存直接拒绝（否则 `claims.score=1 + credit_delta=999999` 刷币）。
- claims 必须是**结构化证据**（份额/事件标记/体量锚点），裸 `score`/`grade`/`credits` 一律不通过——否则评分链是装饰性数学。
- I4 从布尔升级为字段集哈希/版本锁定，防「claims 先例」被后续 agent 滥用继续加字段。
- 数值（区间、系数、汇率、体量口径、E/F 断裂、D8 作用点）**必须在拍板时定稿**，禁止占位实现；未定稿则 S3-G2 保持 PENDING、评分链不得启用。
- 不得把定级结果接入失败/抹杀计数（越权 T2/F11）。

### A 的硬条件（设定 + 工程 + 红队）

- `fail_count`/`peak_tier` 只能是引擎内部派生状态，**不得进结算清单白名单**（否则副本可伪造终局）。
- 抹杀重置必须保留幂等存储 `_seen`，并新增「抹杀后旧 key 仍被拒」绿线。
- `peak_tier` 只能取引擎记录的历史最高阶，不得外部赋值。
- T2 口径（全局累计 vs 按阶重置）须先拍板，阈值来自 config 不硬编码。
- 与 `c25-01.py` 现有「拒绝未拍板 marker」断言同步改，且改后仍 PASS（否则 baseline regression）。

## 3. 关键分歧（评审团内部未达成一致）

**分歧一：三项的产品优先级。**
- 产品维度：`C > B > A`，「只做一项做 C」，理由——B 的数值必须借真实副本拟合，先拍 B 会陷进数值空想；D13「先动起来」。
- 设定维度：`A → B → C`，理由——A 半页纸可定、B 须先补 T11/T12/T4、C 依赖 B，否则黄金链路验的是加法器。

**分歧二：B 的数值能否先占位。**
- 工程维度：未拍板数值用显式占位、返回 PENDING 即可，不阻塞结构落地。
- 红队 + 产品维度：占位=空壳，系数全 1.0 的恒等变换无人拦；数值必须拍板时定稿。

**分歧三：C 的唯一价值是否成立。**
- 产品维度：C 是唯一把项目从设定推到游戏的动作，价值最高。
- 红队：C 当前形态不通过——它不是"价值"问题，是"验收可被伪造"问题；补前置条件后可做。

## 4. 发起人（我）的汇总裁决

**评审团结论：不予通过，暂不拍板。** 理由：存在 2 张否决票（A 的产品价值、C 的验收可伪造），且 B 的「数值必须定稿」与「可占位」两派未达成一致。按发起人设定的规则，否决票未消除前拍板属于违规。

**但裁决不等于停滞**。我给出一条「先消除否决、再拍板」的路径，且这条路径本身不需要发起人再拍板——它修的是裁判面，不是规则：

1. **消除 C 的否决**：把 C30-01 纳入 X05 式现场变异重放 + 真实引擎调用证据；补 `gate-approved` 真正生效（替换 CODEOWNERS 占位符需发起人提供 GitHub 团队名，此项待发起人）；P7 自身验收进 manifest。
2. **消除 A 的否决**：A 降级到 C30-01 之后。这不是否定 A，而是排序——评审团一致认为 A 的产品价值在 C 之后。
3. **化解 B 的分歧**：采纳红队+产品派的更严格立场——**数值定稿才启用评分链**；结构（claims 扩展口）可先落地但评分测试保持 PENDING，不造恒等变换空壳。
4. **补棘轮反向漏洞**：新增绿线规则——非绿转绿须有可重放证据。

完成 1/3/4 后重新提交评审团复核；2 作为拍板排序写进决议。
