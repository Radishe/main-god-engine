## D1 · 惩罚机制重构（推翻旧押金公式）

### 旧设计（已废弃）

> 押金 = min(当前兑换点 × 0.1, 押金上限)

**废弃原因**：该公式锚定玩家**余额**，产生三个漏洞：

1. **花光钱反而风险最小** —— 把兑换点全换成永久资产，押金趋近于 0
2. **惩罚"持有"而非"失败"** —— 实际效果是鼓励立刻消费，与立法意图不符
3. **强者恒强** —— 资产多的人押金高，但他承受力也强，实际相对风险反而更低

### 新设计

**惩罚额锚定任务体量，与玩家有多少钱无关。**

```
惩罚额 = f(任务体量)     ← 与奖励公式结构类似
```

**抵扣顺序（A→B→C）**：

| 顺序 | 抵扣来源 | 说明 |
| :--- | :--- | :--- |
| A | 兑换点 | 优先扣除 |
| B | 属性点 | A 不足时以 B 弥补 |
| C | 物品 | A、B 均不足时以 C 弥补 |
| — | **抹杀** | 累计**三次**失败惩罚 → 抹杀重来 |

**设计意图（原文表述）**：
> 如果优秀的人有胡萝卜吃，劣质的人就得挨板子……扣除和体量相等的东西。

### 待补

- `f(任务体量)` 的具体形式未定 → 见技术债 **T1**
- 「三次失败」是**全局累计**还是**按阶位重置**，与旧文档 09 章细节 2 冲突 → 见技术债 **T2**

## D2 · 高阶进入低阶副本

**原则：原则上不允许。**

若通过**特殊道具**进入，须满足：

| 约束 | 内容 |
| :--- | :--- |
| **阶段限制** | 道具绑定获取阶段与使用阶段。例：二阶获取的道具只能让二阶角色进入一阶副本；角色升到三阶后该道具**失效** |
| **视角限制** | 部分道具只允许以**观察者**身份进入 |
| **任务限制** | 观察者**不触发主线任务以外的任何任务** |
| **收益压缩** | 收益乘以比例系数 |

**收益公式（原文表述）**：

```
二阶进入一阶副本收益 = (3000 ~ 6000) × 比例系数
```

> 其中 `3000~6000` 为一阶副本的正常收益区间。

**获取难度**：此类道具须**提高获取难度**，并与阶段强绑定。

## D3 / D4 · 两层判断，互不冲突

这是本轮讨论澄清的一个**表面矛盾**：

| 层次 | 判断什么 | 依据 | 谁判断 |
| :--- | :--- | :--- | :--- |
| **准入** | 能不能进这个副本 | 玩家**等级/阶位** vs 副本阶位 | **主神** |
| **副本内** | 这个任务扛不扛得住 | 任务**难度** vs 玩家**实力** | **副本自己** |

**关键**：主神**不需要懂综合实力**——它只做粗筛（看等级）。实力判断被**下沉到副本沙盒内**。

> 因此「主神不判定综合实力」与「副本内要看实力」**并不矛盾**，它们是两个层次的职责。

## D7 · 体量切分（滑动变阻器）

**每个副本有一个总体量**，作者在设计时必须**先确立这个总量**，然后把额度**切分**给各个任务：

| 任务 | 占总量比例（示例） |
| :--- | :--- |
| 跑腿送信 | 10% |
| 杀死最终 BOSS | 50% |

**特性**：份额**此消彼长**（类似滑动变阻器）——给简单任务多分，给难任务就少分。

**已察觉的问题**：切分只保证**内部自洽**，不保证**总量合理**。→ 见技术债 **T4**

## D8 · 主线优先（本轮最重要的新增机制）

```
主线任务成功  → 支线收益按 100% 计入
主线任务失败  → 支线收益按 50%（或更少）计入
```

**第一优先级绝对是主线任务。**

### 这一条解决了什么

1. **堵住"刷支线不做主线"的漏洞** —— 不靠禁令，靠**收益权重**引导行为
2. **给了完成度系数一个可计算输入** —— 主线成败是评价的第一个判定点
3. **解释了高级评价的稀缺性** —— 拿 S 必须主线 + 支线双优

> **设计风格**：用收益权重引导，而非用规则禁止。禁令总有绕过方法，权重没有。

### 待补

- 主线失败时，**最高能拿到哪个评价**？（D？E？还是仅降级？）→ 见技术债 **T5**
- 50% 这个系数是否合适 → 属数值拟合

## D9 · 副本是动态库

**原文表述**：

> 副本……用程序员的思维去理解，就是**动态库**。主程序（主神）判定玩家需要进入 A 副本了，就加载 A.dll，或者 A.os。

### 连带结论

| 结论 | 说明 |
| :--- | :--- |
| 副本**可以带自有逻辑代码** | 不是纯 JSON 声明式数据 |
| 08 章 checklist 第 3、11 条**有了意义** | `can_modify_persistent_state = false`、静态扫描 —— 检查的是**副本代码**，不再是"检查表格有没有偷偷联网" |
| 「扭曲节点」**可以实现** | 04 章的规则异常区需要自定义逻辑，DLL 提供了能力 |

### 引发的安全问题

C# 中加载的 DLL **与主程序同进程、共享内存**，可直接反射访问主神状态、修改静态字段、绕过 `settle()`。

**当前立场**：结合 D10，暂不以技术手段强制隔离。→ 见技术债 **T6**

## D10 · 单机 + 开源 + 不在意作弊

**原文表述**：

> 这个单机游戏，且我打算做成开源的，所以就**先不在意是否有"外挂"或者魔改**。

这一条**关闭了多个悬空问题**：

| 原问题 | 结论 |
| :--- | :--- |
| 存档可被编辑/备份 → 永久死亡可被规避 | **接受**。永久死亡的威慑力靠玩家自觉 |

## D12 · 评分链的顺序（修正文档错误）

### 用户指出的问题

> 最终评分好像不是按照结算等级评定的吧？我记得是**按照分值去计算，然后根据分值去定级**的吧？

**用户的记忆是对的，但现有文档写反了。**

| 现有文档的写法（❌） | 正确顺序（✅） |
| :--- | :--- |
| `完成度系数` 是**输入**（查表得到） | 先算**分值** |
| 公式：`基础产出 × 阶位系数 × 完成度系数 × …` | 分值 ÷ 理论最高分 = **达成率** |
| — | 达成率落在哪个**区间** → 定级 |
| — | 用该级系数代入收益公式 |

### 正确链条

```
玩家表现
  → 算出「本次任务得分」（一个数）
  → 与「理论最高分」比较 → 达成率
  → 达成率落入区间 → 定级 S/A/B/C/D/E/F
  → 用该级系数代入收益公式
```

### 概念定义（据此确立）

| 概念 | 定义 |
| :--- | :--- |
| **分值** | 玩家实际拿到的总分（算出来的） |
| **理论最高分** | 副本所有任务满额完成的总分（= 体量） |
| **达成率** | 分值 ÷ 理论最高分 |
| **评价（S~F）** | 达成率落在哪个区间 |
| **完成度系数** | 评价的查表结果 |
| **是否算"失败"** | 看评价是否到 E / F |

## 第二轮决议（2026-11-12，为并行研发派活而拍板）

## D14 · 惩罚体系的设计目的：叙事仪式感

**结论**：惩罚用于提供「轮回有代价」的紧张感与自我约束，**不承担经济平衡职能**。

**与 D1 的关系**：D1 的机制骨架（惩罚额锚定任务体量、与余额无关、三次抹杀）**保留**；但 A→B→C 抵扣链可按此目的简化——优先只扣兑换点，属性点/物品的估值单位与可及性过滤器不再是必需。

**理由**：D10 已确定单机 + 开源 + 不在意作弊，玩家可改存档绕过任何惩罚；为一条可绕过的约束支付统一估值单位、`permanent` 裁决、降阶机制等最贵的工程成本，投入产出比不成立。

**连带关闭/降级**：F3 抵扣链估值单位（降级）、A1 `permanent` 冲突（不再需要裁决）、F16 降阶缺口（不再强制）、C21/C25 的实现复杂度（大幅简化）。

**被否决选项及理由**：「经济平衡优先」（需完整抵扣链，D10 下无效）、「低阶/高阶分层」（两套规则，制造分叉）。

## D15 · 副本贡献模型：JSON 一等公民，DLL 高级通道

**结论**：**声明式 JSON 副本是一等公民**，覆盖绝大多数场景，可机检、可走 Schema validation CI；**带自有逻辑的 DLL 是显式标记的高级通道**，仅用于扭曲节点等确需自定义逻辑的场景，走独立审核流程与权限受限沙盒。

**与 D9 的关系**：**细化，不是推翻**。D9 确定「副本可以带自有逻辑代码」的能力仍然存在，D15 只规定它不再是默认路径。README「不读引擎代码也能写副本」的众创卖点由此成立。

**理由**：JSON 与 DLL 是两套贡献者模型——前者低门槛、可静态验证，后者要求 C# 能力、二进制审核、版本兼容。并存但不分主次，会让 Schema CI 与 08 章「审核者不需理解玩法」同时失效。

**连带**：T6 隔离强度只需对高级通道约定；`C01` / `C12` 的边界判定有了依据；`gates/stubs/loader.json` 的 `code_channel.boundary` 已定稿为 `json_primary_dll_optin`。

**被否决**：「DLL 主路径」（众创门槛过高）、「纯 JSON 取消 DLL」（推翻 D9，扭曲节点落不了地）。

## D16 · 副本内死亡流程（关闭 A7）

**结论**：**死亡 = 立即退出副本，按未完成结算**；不复活；默认计入「三次抹杀」计数；不额外扣资产。`lethal: true` 副本按 07 §5 的既有规则处理。

**与既有表述的关系**：01 §4.1「副本内部的……甚至角色死亡……都是沙盒内的局部状态」**不再作为死亡流程的依据**，仅保留为「副本内状态不直接写入账本」的一般性描述；07 §5「死亡降级为严重失败」的低阶保护表述，按本决议改为「退出并按未完成结算」。

**理由**：堵住「玩家主动送死以逃离高难度任务」的漏洞；且不复活使死亡保有威慑，又不与低阶保护叠加成扣穿属性的死循环。

**连带**：`C25` 抹杀态语义有了入口；`droppable` 概率掉落仍按 06 §2 执行；`S2-G3-02` 的行为断言现在可以写实。

**被否决**：「复活继续」（死亡无威慑，永久死亡保护变多余）、「直接计为严重失败」（需补降阶机制，链条更长）。

## D17 · 技术栈：Python 原型优先

**结论**：**先用 Python 跑通「主神引擎 + JSON 副本加载 + 结算循环」**，呈现层与 Unity 选型**推迟到最小闭环跑通之后**再定。门禁、validation CLI、测试工具链统一用 Python 标准库。

**与 01 §7 的关系**：**不否定**「Unity 远比 UE5 合适」的论证，只按 D13 把选型时点后移——引擎选型的真实约束是 D15 的加载路径与工具链门槛，而非 2D 渲染能力；在架构未验证前锁死引擎没有必要。

**理由**：当前 0 行实现、6 个工作包处于 `BLOCKED`；Python 工具链已建成，选它可让 P1/P2/P3/P4/P7 立即开工，无需等待 Unity 工程结构。

**连带**：`config/paths.json` 登记 `<test-runner>` 与 `<engine-core>`；`<render_profile>` 在原型阶段只做元数据占位，不做真实管线切换。

**被否决**：「Unity 6 + C# 运行时即刻启动」（两套语言、贡献者需装编辑器）、「TypeScript 全栈统一」（推倒已建工具链，且与 01 §7 冲突）。

## D18 · claims 扩展口与 D12 评分链（评审团附条件通过，2026-11-25）

**结论**：把 `settle()` 从「加法器」升级为「规则引擎」——副本通过版本化 `claims` 申报**结构化证据**（分值、体量、主线/支线份额、事件标记），主神侧按 D12「分值 → 达成率 → 定级 → 系数 → 兑换点」独立算分定级。

**硬约束（缺一即不合规，实现期 DoD）**：

1. `credit_delta` 在**所有 completion** 下停止作为 credits 权威来源；claims 与 credit_delta 双字段共存即拒绝（防双报刷币）。

3. I4 从布尔 `frozen` 升级为**字段集哈希/版本锁定**；字段集扩展须同时改哈希并经 `@Radishe` 独立审批，防「claims 先例」被滥用。
4. 评分数值（达成率区间、各档系数、汇率、体量口径、E/F 断裂修复、D8 作用点）**必须在启用评分链前定稿**；未定稿期间 S3-G2 保持 `PENDING`，评分链不得启用——**PENDING 的原因只能是「实现未写」，不能是「数值未定」而假装已就位**。
5. 不得把定级结果接入失败/抹杀计数（越权 T2/F11）；D15 已简化惩罚为只扣兑换点。
6. `src/core/scoring.py` 只认 claims 中性键，不得出现具体属性轴字面量（过 I2 扫描）；X02 补「双报拒绝」黑盒探测；mutation recipes 补「双报」「claims 造币」两条配方。

**与 D12 前置的关系**：T11（份额是否加总 100%）、T12（体量是否 = 理论最高分）、T4（体量总量标准）、E=0/F 无值等未拍项，按约束 4 在启用前定稿；本决议不代替拍板这些数值，只锁定「必须定稿才启用」的规则。

