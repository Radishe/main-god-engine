## T1 · 惩罚函数 `f(任务体量)` 的具体形式

**状态**：未定 ｜ **严重度**：高

### 问题

决议 D1 确定「惩罚额锚定任务体量」，且「和奖励计算公式类似」。但**"类似"是个危险的词**——具体形式未定。

**待定**：惩罚是

- `体量 × 固定失败系数`？
- `体量 × 评价对应系数`（即复用完成度系数表）？
- 还是与奖励完全同构、只是系数不同？

### 为什么重要

这决定玩家**失败一次的代价**，是所有风险决策的基准。若惩罚过轻，D6 的"作死抹杀"失去威慑；若过重，玩家不敢进副本。

### 相关

- 影响 D6 的可行性与 07 章全部惩罚表
- 与 T12 耦合：若"体量 = 理论最高分"，则惩罚可直接复用完成度系数表

## T2 · 「三次失败抹杀」：全局累计还是按阶位重置

**状态**：**与旧文档矛盾** ｜ **严重度**：高

### 问题

- **本轮讨论（D1）**：累计**三次**失败惩罚 → 抹杀。未说明是否重置。
- **旧文档 09 章细节 2**：倾向「按阶位重置，高阶容错更低（一阶 3 次、二阶 2 次、三阶以上 1 次）」。
- **旧文档 07 章第 3 节**：已按"按阶位重置 + 3/2/1"写入正文。

### 矛盾点

三处说法不一致：

| 出处 | 次数 | 是否重置 |
| :--- | :--- | :--- |
| 本轮 D1 | 固定 3 次 | 未说明 |

| 07 章正文 | 3 / 2 / 1 | 按阶位重置 |

**问**：D1 的"三次"是"最低阶三次"的意思（即与 3/2/1 一致），还是**改成固定三次**（推翻按阶位重置）？

### 为什么重要

这是永久死亡的触发器。**必须与 T8/T9 一起看**——因为在单机 + 可读档下（D10），无论用哪个方案，都只能靠玩家自觉。

## T3 · 「收益与风险是否成正比」如何量化

**状态**：思维盲区 ｜ **严重度**：高

### 问题

D6 规定：明知故犯挑战远超自身规格的任务 → 该抹杀。判定依据是「**任务收益和任务风险是否成正比**」。

**但"成正比"目前没有可执行的定义。**

### 需要回答

- 「风险」用什么数表示？任务难度标注？玩家战力？两者的比值？
- 「收益」用任务体量？还是该副本的平均收益？
- "成正比"的判定阈值是多少？
- 假设"不成正比 = 抹杀"——**那低风险低收益的正经副本也会被判"不成正比"吗？**

### 为什么重要

这是 D6 唯一的执行细节。**没有它，D6 无法落地。**

### 备注

用户在讨论中明确表示这是**未想清楚的部分**。与 T4 是同一片盲区的两个侧面。

## T4 · 体量总量的标准 ★ 最核心的未解问题

**状态**：**思维盲区（用户明确表示"没有思路"）** ｜ **严重度**：最高

### 问题

D7 确定"体量按任务份额切分"，但**只解决了分配，没解决总量**。

作者可以申报任意虚高的总量：

| 任务 | 份额 |
| :--- | :--- |
| 跑腿送信 | 10% |
| 杀死 BOSS | 50% |

份额加总 100%，**内部自洽**，但"总量 = 100000"这个数**无人约束**。

### 用户原话

> 这个我还是没有什么好的思路和方向，也就是这个所谓的"标准"。

### 可选的三个方向

| 方案 | 谁定总量 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **A. 作者申报** | 作者 | 简单 | 虚高无法约束（现状） |
| **B. 主神按阶位设上限** | 主神 | 无需人工；复用已有零件 | 需要阶位↔体量对照表 |
| **C. 实测收敛** | 首次通关数据 | 最可靠 | 需要作者自测（用户已表示不需要，见 T4.1） |

### 重要线索（Lead 发现）

**用户已有的 09 章「阶位与评分区间」表，可能就是这个标准：**

| 项目 | 占位值 |
| :--- | :--- |
| 新手 / 一阶分界 | 1000 |
| 一阶区间 | 1000 ~ 2999 |
| 二阶区间 | 3000 ~ 5999 |
| 十阶下限 | 768000 |
| 区间增长方式 | 每阶翻倍 |

**该表标题本就写着"评分区间"** —— 说明它原本就在定义"每个阶位对应的分值范围"。

**若成立**，则标准可表述为：

> **一阶副本的总体量必须落在 1000~2999；二阶副本必须落在 3000~5999。**

这同时**接通了 08 章 checklist 第 6 条**：

> 6. 推导出的副本阶位与任务分值设计匹配（无畸高单任务）

**即：该 checklist 项描述的就是这个机制，只是从未与 09 章的表联系起来。**

### 待确认

1. 体量区间是**复用**玩家阶位区间，还是**单独设**一张？（副本阶位 vs 玩家阶位是否同一套刻度）
2. 若复用，如何界定"体量落在哪一阶"——取区间下限、上限还是中值？

<a id="t4-1"></a>
### T4.1 · 是否要求「作者附通关记录」

**用户立场：不需要。** 理由：

> 如果这个**体量总量的标准**指定成功了，哪怕副本写的是一坨屎，只要能被"主神"收录量化，那就是**可用的副本**。

**评估**：这个理解是**成立的**，且比"作者自测"更简洁——因为**有了总量标准，虚报空间已被上限压缩，不需要再靠自测验证**。

**结论**：T4.1 **依赖 T4**。T4 解决后此项自动关闭。

## T5 · 主线失败后的评价上限

**状态**：未定 ｜ **严重度**：中

### 问题

D8 规定"主线失败 → 支线按 50% 计"。但**未说明主线失败后，最高能拿到哪个评价**。

### 两种可能

| 方案 | 含义 | 后果 |
| :--- | :--- | :--- |
| **A. 仅扣分** | 主线失败只是拉低总分，若总分仍高（支线极多）仍可能拿 B | 可能被"海量支线"绕过主线 |
| **B. 设上限** | 主线失败 → 评价最高只能到 C（或 D） | 彻底堵死绕过路径 |

**用户倾向**：从"体现了高级评价的稀缺性"这一表述看，**倾向 B**。

### 待确认

- 上限设在哪一档？
- 该档是否触发惩罚（即"主线失败算不算失败"）？

> **关联**：用户曾问"最终评分不是按分值算的吗"（见 D12）——按 D12 的链条，主线失败**先扣分再定级**，那么"上限"可能不需要单独设，而是**扣分自然导致降级**。需确认取哪种。

## T6 · 副本 DLL 的隔离强度

**状态**：已知问题，暂不处理 ｜ **严重度**：中

### 问题

D9 确定"副本 = 动态库"。C# 中加载的 DLL **与主程序同进程、共享内存**，因此可以：

- 反射调用主神内部类（`Type.GetType("MainGod.PlayerState")`）
- 直接改静态字段（`PlayerState.Credits = 999999`）
- 绕过 `settle()` 唯一入口

**这与 01 章"副本永远不能直接写主神状态"的纪律直接冲突。**

### 三个层次的方案

| 方案 | 做法 | 能否防住反射 | 复杂度 |
| :--- | :--- | :--- | :--- |
| A. 约定式 | 文档规定 + 人工检查 | ❌ | 最低 |
| B. 接口隔离 | 副本只拿到只读快照 + 提交清单方法 | ⚠️ 防君子 | 低 |
| C. 进程/域隔离 | 独立 AppDomain / 独立进程 + 序列化通信 | ✅ | 高 |

### 当前立场

结合 D10（单机、开源、不在意作弊），**用户明确表示技术实现可以滞后**（D13）。

**但需注意**：这意味着 08 章 checklist 第 3 条（`can_modify_persistent_state = false`）与第 11 条（静态扫描）—— 

- 若采用 A，这两条应改写为**人工审查**
- 若采用 B/C，才名副其实为"静态扫描"

**待确认**：checklist 这两条的措辞是否要调整。

## T8 · ★ 时间轴与存档的冲突（用户自称的盲点）

**状态**：**思维盲区** ｜ **严重度**：高

### 用户原话

> 如果不能保存，则玩家玩得太累；如果能保存的话，**主神主程序的时间轴就被卡住了，形同虚设**。玩家只需要随便进入一个副本，然后退出保存，则永远不会触发时间轴的提示机制。

### 拆解：这其实是两个不同的问题

用户把它们当成一个，**但它们可以分开解决**：

| # | 问题 | 本质 | 状态 |
| :--- | :--- | :--- | :--- |
| **A** | 存读档是时间旅行 | **不可逆性**问题 | **已由 D10 关闭**（不在意作弊） |
| **B** | 进副本就冻结主神倒计时 | **计时基准**问题 | **未解（本轮重点）** |

### 关于 A

用户已明确"不在意作弊"（D10）。**读档 = 作弊的一种**。因此 A **已被接受，不需要技术解决**。

### 关于 B —— 这才是真问题

**B 与作弊无关，正常游玩就会发生**：玩家进副本 → 时间轴冻结 → 无论玩多久时间轴都不动。

### 可能的解法（待用户确认）

**核心思路：副本不是"暂停时间轴"，而是"消耗时间轴"。**

| 模型 | 含义 | 副本内如何 |
| :--- | :--- | :--- |
| A. 现实时间 | 跟随玩家真实生活 | 现实时间照走，副本须限期内完成 → **会被"永不上线"卡死** |
| B. 游戏内时间 | 只在主神空间流逝 | 进副本 = 暂停 → **仍会被存档卡死** |
| **C. 混合** | 主神空间按 A，副本内按 B，**副本耗时折算进时间轴** | 副本**消耗**时间，不暂停 → **问题消失** |

**Lead 的观察**：用户的架构**强烈指向 C**，因为：

- 01 章已确立"副本世界是另一个时空"（无限流标配）
- 02 章有"逾期未进入副本"的惩罚 → 说明主神空间确实有倒计时

**在 C 模型下，T8 自动消失**，因为时间轴的计时点是**"进入副本"和"离开副本"两个瞬间**，与玩家中途存不存档无关。

### 待用户确认

> **时间轴是"玩家多久没进副本就惩罚"（现实时间），还是"玩家在主神空间待了多久"（游戏内时间）？**

**Lead 判断用户要的是后者。**

## T11 · 主线/支线份额是否必须加总 100%

**状态**：**矛盾** ｜ **严重度**：高

### 问题

D7 说"体量按任务份额切分"，示例中 10% + 50%，但**没说是否必须加总 100%**。

### 两种设计的后果

| 设计 | 后果 |
| :--- | :--- |
| **必须加总 100%** | 理论最高分 = 体量，玩家满额完成刚好触顶 → **体量 = 理论最高分** |
| **可以不到 100%** | 理论最高分 < 体量 → **申报的体量永远达不到（虚高）** |

### 为什么重要

**这直接决定 T12**：体量与理论最高分是不是同一个数，进而决定 D12 里"达成率"的分母。

**Lead 建议**：应**必须加总 100%**，否则体量的定义就失去意义。
