# 无限流 · 主神框架

> 项目愿景 + 文档导航 + 当前阶段

---

## 1. 一句话愿景

做一个**无限流**题材的游戏：把「主神」做成一套**开源的规则与状态引擎**，把剧本做成**社区可贡献的数据**。框架上传 GitHub，让所有人为框架填充副本剧本，形成众创。

无限流题材的天然优势：它对「缝合」概念本来就兼容，不需要粉饰——各种世界观、各种玩法、各种呈现形式都可以并存，只要收敛到同一套主神规则之下。

---

## 2. 核心架构判断

### 2.1 权责边界：主神是规则引擎，不是剧本本身

「主神」应该是一个**规则与状态管理引擎**，负责：

- **轮回者状态**：属性、技能、兑换点、装备、永久死亡标记。
- **副本准入与结算**：任务生成、完成条件判定、奖励发放、失败惩罚。
- **跨副本持久化**：从 A 副本带出的能力如何在 B 副本中生效（或失效）。
- **兑换系统**：用统一的数值词汇表定义「血统、功法、道具」的 cost 与 effect。

社区贡献的剧本**只描述「这个副本里有什么、会发生什么」，不触碰主神的规则实现**。否则每个剧本都自带一套私有规则，框架会迅速失控。

### 2.2 副本有自主性，但硬性框架必须在主神之内

**结论：可以实现。** 这不是「缝合怪」，而是一个**分层架构**：副本拥有高度的内部自主权，但主神保留**结算权**与**状态持久化权**。

真正的难点不在「能不能切换」，而在「切换时如何保证主神的状态不被副本污染」。

核心机制：

- **引擎对数值「语义无知」**：引擎持有一个开放字典 `attributes`，遍历所有 key 做通用结算，但不关心 key 叫什么。生存副本用 `{hp, hunger}`，战斗副本用 `{hp, atk, def}`，引擎完全兼容。
- **属性名称与含义由副本定义**，但**存储格式、更新方式和边界规则**（如数值范围 0–100）由主神引擎统一持有。
- **视觉切换是「管线切换」，不是「引擎重写」**：把视觉风格做成副本元数据（`render_profile: "3d" | "2d_flat" | "graffiti"`），主神加载时把渲染权交给对应管线。

### 2.3 收益转换：主神是唯一的「账本」，副本只是「临时工作区」

副本结束时，只向主神提交一份**标准化的结算清单**：

```
副本 ID / 轮回者 ID / 完成状态
兑换点增量（整数）
永久性能力变更（引用主神词汇表的 ID 列表）
携带出副本的物品（引用主神物品表的 ID 列表）
```

主神收到清单后，用自己的规则做转换和落账。**副本作者不需要知道主神空间的兑换汇率**，他只需要按 Schema 填写「这个副本产出了什么」；汇率、稀有度映射、跨副本平衡性调整，全部由主神层的维护者控制。

**副本的「自主性」止步于结算接口，主神的「硬框架」体现在接口背后的计算规则上。**

### 2.4 第一优先级不是 3D，而是定义接口

经查证，GitHub 上**不存在**同时具备「3D 呈现 + 主神规则引擎 + JSON 剧本众创」的完整项目。但每一块拼图都有可参考或可复用的现成项目（详见 [01-核心设计哲学.md](01-核心设计哲学.md)）。

因此：**第一优先级是定义那个接口**——一个副本的 JSON Schema 长什么样，它引用哪些场景资产 ID、事件节点如何与 3D 触发器绑定、结算谓词如何调用主神引擎的轮回者状态。

## 4. 当前阶段

**阶段：概念设计基本成形，等待拍板 → 即将进入 JSON Schema 设计。**

项目自身规划的落地顺序：

1. **不要先做 3D。** 先用数据驱动思路，在 2D 或极简 3D 原型里把「主神规则引擎 + JSON 副本加载 + 结算循环」跑通。
2. **把 Schema 和 validation CLI 做扎实。** 这是社区众创的命门。
3. **Agent 用在「降低贡献摩擦」上，而不是「替代贡献者」。**
4. **先建治理文档，再开 PR。**

### 建议的最小验证方案

第一版**不需要**同时支持 3D、2D 和涂鸦。先做最简的异构验证：

- 副本 A：「3D 小房间里的战斗」，用 `{hp, atk, def}`
- 副本 B：「2D 平面上的生存」，用 `{health, hunger}`
- 两者通过**同一个主神结算接口**提交清单，主神把结果映射到同一套兑换点

**只要这两个异构副本能无缝切换且主神账本不被污染，架构就验证通过了。** 之后加涂鸦风格、加更多属性轴，都是往已经稳定的接口上追加配置，而不是重新设计。

### 下一步

1. 确认七个待钉死的细节（见 [09-待确认细节.md](09-待确认细节.md)）。
2. 确认数值占位表的方向（只需增长曲线形状）。
3. 进入 JSON Schema 设计：副本提交格式、结算清单格式、物品注册格式。
4. 编写最小结算引擎的伪代码。
5. 在 Unity 端实现加载器和结算循环的原型。

### 关于素材 A 的获取过程

分享链接的 API **单次返回量不足以取回全部 16 轮**：本次抓取实际返回 127,570 字节（约 124.6 KiB / 100,255 字符）后即被截断，且返回内容的大部分被 Deep Search 的搜索结果元数据占据，导致**助手第 3 轮起的回答无法通过接口取得**。

> 注：该接口不接受分页参数（`offset`/`limit`/`message_id`/`format` 均被忽略），始终从第 1 条消息开始返回，因此无法通过分页绕开截断。

最终通过用户导出的 HTML（渲染后的完整 DOM）解析出全部 16 轮内容。

### 数值的严格区分

> **重要**：文档中出现两类数值，必须区分：
