## 1. 权责边界

### 1.1 主神 = 规则引擎，剧本 = 数据

> 来源：turn 2

「主神」应该是一个**规则与状态管理引擎**，而不是剧本本身。它负责四件事：

| 职责 | 内容 |
| :--- | :--- |
| 轮回者状态 | 属性、技能、兑换点、装备、永久死亡标记 |
| 副本准入与结算 | 任务生成、完成条件判定、奖励发放、失败惩罚 |
| 跨副本持久化 | 从 A 副本带出的能力如何在 B 副本中生效（或失效） |
| 兑换系统 | 用统一的数值词汇表定义「血统、功法、道具」的 cost 与 effect |

**社区贡献的剧本，只描述「这个副本里有什么、会发生什么」，不触碰主神的规则实现。**

> 否则每个剧本都自带一套私有规则，框架会迅速失控。

### 1.2 副本自主性 vs 硬性框架

> 来源：turn 6（助手回答）

**结论：可以实现。** 用户描述的不是「缝合怪」，而是一个**分层架构**：副本拥有高度的内部自主权，但主神保留**结算权**与**状态持久化权**。

> 真正的难点不在「能不能切换」，而在「切换时如何保证主神的状态不被副本污染」。

副本可以有自己的玩法与呈现，但收敛点只有一个：

- 副本场景**不局限于 3D**，人物**不局限于单一角色**，角色属性**不强制统一**。
  - 生存副本：只需要健康和饥饿状态。
  - 战斗副本：需要力、敏、体、智等属性。
  - 新手关卡：另一套简化结构。
- 呈现形式可以逐副本切换：3D → 2D 平面 → 涂鸦风格。
- **硬性框架必须在主神之内**：副本结束时，收益必须按主神的计算规则换算成主神框架中的属性收益。

> 换句话说：**Agent / 副本生成的是「副本里的东西」，不是「副本在无限流框架中的位置」。**（turn 4）

### 1.3 惩罚的执行者

**惩罚的执行者永远是主神引擎，不是副本脚本。** 副本只能申报「失败」这个事件，后果由主神裁定。（详见 [07-惩罚与死亡机制.md](07-惩罚与死亡机制.md)）

## 2. 核心机制：引擎对数值「语义无知」

> 来源：turn 6

这是让「副本自定义属性」得以成立的底层设计。

- **引擎的核心是一个开放字典 `attributes`**，遍历所有 key 做通用结算，但不关心 key 叫什么、代表什么。
- 规则怪谈模式用 `{hp, san}`，末日生存模式用 `{hp, hunger}`，**引擎完全兼容**。
- 加一个新副本类型，只需要一条「元数据」声明这个副本有哪些数值轴，**不需要改引擎核心**。

**权责划分**：

| 归属 | 内容 |
| :--- | :--- |
| **副本定义** | 属性名称、属性含义 |
| **主神统一持有** | 属性的存储格式、更新方式、边界规则（如数值范围 0–100） |

副本可以在自己的沙盒里跑一套完全不同的属性系统，**结算时把结果映射回主神账本**即可。

**佐证**：EVEngine 的 RPG 模块遵循同一原则——属性名、效果 ID 全部使用**字符串**而非编译期枚举，新增一个属性不需要改引擎头文件、不需要重新编译，数据可以完全放进 JSON 由策划配置。

> 这意味着社区贡献者写一个新副本时，声明自己的属性集就像**写一行配置**，而不是提交一段代码。

## 3. 视觉层：管线切换，不是引擎重写

> 来源：turn 6

「上一个副本 3D，下一个 2D 平面，再下一个涂鸦风格」在渲染层面是成熟的。

- **Unity**：运行时管线切换方案以渲染契约抽象为底座，可根据场景需要实时切换写实渲染、风格化渲染等不同管线，而不必重构底层逻辑。
- **Godot**：架构模式天然支持——每个场景可拥有独立视觉表现，全局状态通过 AutoLoad 单例或共享状态插件跨场景保持，**场景切换时只替换呈现层，不触碰数据层**。

**做法**：把「视觉风格」做成副本元数据的一部分。

```
主神引擎加载副本 → 读取 render_profile: "3d" | "2d_flat" | "graffiti"
                → 把渲染权交给对应管线
```

主神自身**不知道也不关心**这个副本长什么样，它只负责在结算时从副本接口拉取收益数据。

> 该机制对应 [09-待确认细节.md](09-待确认细节.md) 细节 7（视觉风格倾向纯表现层，选项 A）。

## 4. 收益转换与状态隔离

### 4.1 主神是唯一的「账本」

> 来源：turn 6

**副本内部的一切（积分、道具、临时能力、甚至角色死亡）都是副本沙盒内的局部状态，不直接写入主神账本。**

副本结束时，只向主神提交一份**标准化的结算清单**：

```
副本 ID / 轮回者 ID / 完成状态
兑换点增量（整数）
永久性能力变更（引用主神词汇表的 ID 列表）
携带出副本的物品（引用主神物品表的 ID 列表）
```

主神收到清单后，用自己的规则做转换和落账。**副本作者不需要知道主神空间的兑换汇率**——他只需按 Schema 填写「这个副本产出了什么」；汇率、稀有度映射、跨副本平衡性调整，全部由主神层维护者控制。

> **副本的「自主性」止步于结算接口，主神的「硬框架」体现在接口背后的计算规则上。**

### 4.2 真正的工程难点：状态隔离

> 来源：turn 6

架构上把「副本沙盒」和「主神账本」分开后，最需要守住的纪律是：**副本永远不能直接写主神状态**。

- 副本**可以读取**进入时的快照（轮回者当前属性、携带物品）。
- 副本的所有修改都发生在**自己的局部状态**里。
- 只有主神收到结算清单后，才执行**一次性的、经过校验的写入**。

这对应分布式系统中的**快照隔离**（snapshot isolation）模式：一个操作在它的一致性快照中执行，外部看不到中间状态，只有在提交时才一次性生效。

> **简化实现**：不需要一上来就做分布式系统那么重的实现。一条规则就够——
> **主神的 `settle(副本结算清单)` 是唯一能修改轮回者永久状态的入口**，副本代码和副本数据在任何情况下都不能直接操作这个入口之外的主神状态。

### 4.3 商业验证

> 来源：turn 6

Steam 上的《主神的游戏》已经商业验证了这个模式：**九个世界各有完全独立的规则、战斗方式和通关思路**，但完成后统一回到主神空间，用技能芯片和血统进行跨副本的永久成长。

它的「收益转换」不是把副本内的数值直接搬出来，而是把副本内的成就**抽象成主神空间可识别的成长货币**。

## 5. 小说蓝本：三种主神哲学

> 来源：turn 12 / turn 14 / turn 16。**以下均为参考作品的设定**，用于说明设计思路，不是本项目已采纳的数值。

### 5.1 《轮回乐园》——「乐园阵营」：放养但可控

用户提出的核心参照：主神的规则范围与《轮回乐园》的乐园阵营类似——**给副本一些自主性，但总归在主神的规则之内**。

助手的判断：这个直觉很准。乐园阵营提供了近乎完美的蓝本——**它不直接干涉副本内部怎么玩，但它垄断了「什么算数」的定义权**。

#### 核心契约：用「公证」取代「统一」

| 规则 | 内容 |
| :--- | :--- |
| **入场公证** | 副本加载时，主神只做三件事：校验副本声明的「属性轴」是否符合底层数据格式规范；确认副本引用的场景资产 ID 在库；**冻结轮回者进入时的状态快照** |
| **产物公证** | **未经主神公证的物品或能力，只能在当前副本内使用，无法带出** |

> 产物公证这条规则直接堵死了副本作者通过私自定义超模道具来破坏跨副本平衡的可能——**东西可以用，但想变成「永久资产」，必须走主神的结算通道。**

#### 收益结算：主神拥有最终「定价权」和「评级权」

主神结算时不关心副本内部的经济系统，只认几个抽象指标：

- **世界之源 / 战斗贡献**：副本结束时，主神根据轮回者在副本内的行为（击杀、探索、任务完成度）统一折算为贡献值，再按比例转化为主神空间通用货币。
  - 小说设定示例：战斗贡献值 0.1% = 乐园币 50。**（此为小说数值，非本项目数值）**
- **强制评级与晋升**：主神根据结算数据对轮回者做世界结算评价（如 S-、A 级），并可能强制调整权限等级。例如当检测到轮回者实力远超当前阶位上限时，**强制提升其等级并开启晋升试炼**，而不是任由其在低阶副本里「炸鱼」。
- **属性上限锁**：主神对「裸装属性」设有硬性门槛。副本里可以给你临时 buff，但**永久属性点的投放权必须握在主神手里**。
  - 小说设定示例：任意裸装属性达到 50 点才满足某些晋升条件。**（此为小说数值，非本项目数值）**

> 副本作者只需要在结算清单里填写「本次产出：战斗贡献 X 点、可公证物品 ID 列表」，换算汇率和稀有度映射完全由主神侧的配置文件决定。**副本的自主性止步于产出申报。**

#### 越界惩罚：双向约束

- **对副本作者的约束**：如果副本试图绕过公证接口直接写入主神账本，或在副本内植入恶意脚本，主神应具备**直接拒绝加载该副本或强制回滚**的能力。副本的「自主性」必须运行在一个**权限受限的沙盒**中——它只能读取快照，不能触碰持久化存储。
- **对轮回者的约束**：主神可定义违规行为（如利用副本机制漏洞刷取收益），并设置从「收益清零」到「永久死亡标记」的阶梯惩罚。**惩罚规则的执行者必须是主神引擎，而不是副本脚本。**

#### 权限分级：副本的自主性本身也分等级

| 副本层级 | 主神干预度 |
| :--- | :--- |
| 低阶 / 新手副本 | 属性轴极简（如只有健康和饥饿），主神对副本内部规则干预度最低，几乎完全放手 |
| 高阶副本 | 副本可拥有更复杂的内部规则（如完整的力敏体智系统），但**结算时的校验项也更多、更严格**；产物需经过更严格的公证（如「完全公证」vs「自由公证」，后者属性部分保密但公证费更低） |
| 晋升试炼 | 主神指定特殊副本作为试炼场，**该副本的结算规则由主神直接注入，副本作者无权修改** |

> 注：「完全公证 / 自由公证」是小说中的机制，可作为本项目公证分级的参考方向。

#### 最小闭环

> 「公证-结算-惩罚」三件套构成「**自主性在副本，终裁权在主神**」的最小闭环：
> 1. **公证接口**是副本获得「合法身份」的唯一入口；
> 2. **结算清单**是副本向主神「报税」的唯一通道，主神拥有汇率和评级的单方面定价权；
> 3. **沙盒权限**确保副本永远无法绕过接口直接篡改主神账本，越界即被拒绝或回滚。

### 5.2 《无尽武装》——「可博弈的制度机构」

> 来源：turn 14

与《轮回乐园》**并不完全类似**：在「副本自主性」和「结算惩罚」上有相似的功能性，但**底层权力结构截然不同**。

- 《轮回乐园》：乐园是一个近乎绝对的、**人格化的规则化身**，它的意志就是终裁。
- 《无尽武装》：顶层是一个更复杂、甚至**可以被渗透和对抗的政治实体**——「议会·主宰」的二元结构，存在「最高议会」与「主宰」两股势力，甚至有最高议会与主宰都无法拥有权限的特殊存在。

> 意味着《无尽武装》里「主神」的规则**不是不可质疑的铁律，而是一个充满漏洞、可以被研究、利用甚至篡改的系统**。

**副本自主性的不同驱动逻辑**：《无尽武装》引入了「血腥都市」与「荒野」的二元结构。

| 区域 | 特征 | 类比 |
| :--- | :--- | :--- |
| 血腥都市 | 基础、有限但风险可控的稳定收益 | 主线副本 |
| 荒野 | 收益特殊且无上限，风险难以估计 | 高自由度的开放世界 / 隐藏副本 |

**对本项目的启示**：副本的「自主性」可以不仅是风格上的（3D/2D），还可以是**风险与回报结构上的分层**。可设计「标准公证副本」和「未公证 / 荒野副本」两类通道，后者允许更高收益和更离谱的规则，但**主神不为其内部平衡性背书**，结算时进行更严苛的审查或折价。

**结算**：硬通货是「血腥点」（小说设定）。任务有明确的**基准分**，完成奖励点数，失败扣除点数，**点数不足者直接抹杀**。小说中也体现了对通胀的严格控制。

**关键区别在于「谁在制定价格」**：《轮回乐园》的定价权属于一个超然的规则意志；《无尽武装》的定价体系存在于一个**可以被「聪明人」利用漏洞**的环境中。

#### 两种主神哲学对照

| 设计维度 | 《轮回乐园》式（绝对规则化身） | 《无尽武装》式（可博弈的制度机构） |
| :--- | :--- | :--- |
| 主神本质 | 不可质疑的终裁者 | 有漏洞、可被研究/利用的复杂系统 |
| 规则刚性 | 高，规则即铁律 | 相对较低，规则是博弈的棋盘 |
| 玩家策略 | 在规则内寻求最优解 | 寻找规则漏洞，尝试「超越」或「利用」系统 |
| 副本自主性 | 通过「公证」接口进行受控的放权 | 通过「都市/荒野」的风险分层来实现 |
| 框架风险 | 较低，但可能抑制「刁民」创造力 | 较高，需要强大的反作弊和动态平衡能力 |

> **取舍**：如果希望鼓励社区作者和玩家钻研、试探甚至「玩弄」规则，《无尽武装》式的主神会提供更肥沃的土壤。但代价是——主神不能只是一个静态的结算接口，它必须是一个**能够感知、分析并响应规则滥用的动态系统**，这比实现单纯的「公证-结算」闭环复杂得多。

### 5.3 《无限恐怖》《王牌进化》《惊悚乐园》——三个岔路口

> 来源：turn 16

#### 《无限恐怖》：原点与不可动摇的硬约束

主神是一个**功能高度集中的黑箱**，只负责三件事：发布强制任务、提供兑换强化、控制时空穿越。轮回者没有选择权，只能在「完成或抹杀」的二元规则下求生。

- **启示：「惩罚的确定性」**——奖励体系可以复杂（奖励点 + 支线剧情），但**惩罚必须简单、明确且由主神单方面强制执行**，比如点数耗尽即抹杀。
- **基因锁设定**：突破只能在**生死边缘的副本内触发，主神无法直接赋予**。这暗示框架可以设计一些**只在副本内部才能获得、但结算后能被主神公证**的「稀有成长路径」，以此激励玩家冒险，同时保持主神的最终裁决权。

#### 《王牌进化》：从「黑箱」到「可运营的系统」

关键进化：把主神空间从「中转站」扩张成一个独立的「第三世界」。轮回者不再只是任务间隙匆匆兑换，而是可以在空间内**交易、交流、形成工会**。

> 意味着主神框架从纯粹的「任务发布器 + 商店」，变成了一个**具备内部社会与经济系统的持久化平台**。

- **场景规则分层**（重点借鉴）：副本被区分为「和平场景」「掠夺场景」「契约场景」等类型，不同场景适用完全不同的底层交互规则（如能否 PVP、交易是否受保护）。
  > 这比单纯按「视觉风格（3D/2D）」分层更进一步——**它按玩家间的交互规则来定义副本性质**。框架可引入类似的「场景规则标签」，让副本作者在申报时选择，主神据此在结算时套用不同的公证与税率规则。
- **扭曲节点**：在遵循原作地理逻辑的世界中，植入如楼梯幻境、青铜巨门等**规则化空间折叠**——一种在不破坏副本世界观自洽性的前提下注入超规则机制的方法。副本作者可在写实风格副本中嵌入一个规则完全不同的「异常区域」，**主神只需认可这个「异常区域」作为一个合法的结算单元**。

#### 《惊悚乐园》：最激进的「元规则」视角

本质上是一个虚拟现实游戏，其存在本身就是一个由神魔设计的「赌斗场」。两个独特机制：

- **「真实性即规则」**：副本世界严格遵循物理逻辑与叙事逻辑，玩家的行为会触发**不可逆的世界反馈**。例如丧尸的肉可作为体能补给，锻造出超越系统评级的神器会直接导致物品「品质溢出」。
  > 意味着主神**不再需要预先定义一切可能性**。如果允许副本内部存在一套自洽的物理/因果模拟，那么玩家基于这套逻辑产生的「预期外行为」，主神可以在结算时将其识别为**合法的、甚至高价值的「技巧值」来源，而不是视为漏洞**。
- **「元规则」治理**：惊悚乐园的主神之上还有「神魔赌局」的策划者，游戏内管理员（GM）也拥有不同的权限层级。
  > 对众创框架的治理结构有直接启发：**主神可以不是唯一的「神」**。可设计分层权限体系——顶层是框架维护者（定义公证汇率、惩罚阶梯等基础规则），中层是副本审核者（拥有加载/拒绝副本的权限），底层才是副本作者与玩家。**这能在保持「主神终裁」的同时，将一部分治理责任下放，避免维护者成为唯一瓶颈。**

#### 三作整合

| 小说 | 核心贡献 | 可落地的机制 |
| :--- | :--- | :--- |
| 《无限恐怖》 | 硬约束与确定性惩罚 | 强制任务与抹杀规则由主神引擎单方面执行；设计仅在副本内触发的稀有成长路径（如基因锁），结算时由主神公证 |
| 《王牌进化》 | 系统扩张与规则分层 | 主神空间设计为可交易的持久化平台；引入场景规则标签（和平/掠夺/契约），主神据此差异化公证；允许副本内存在「扭曲节点」式的规则异常区 |
| 《惊悚乐园》 | 真实性模拟与元治理 | 允许副本内部自洽的物理/因果模拟，预期外但合乎逻辑的行为可被结算为高价值产出；设计分层治理结构 |

> **共同结论**：主神不必是一个全知全能、事无巨细的规则定义者。它可以是一个**薄而坚硬的裁决层**（《无限恐怖》的强制力），架设在一个**可运营的持久化平台**（《王牌进化》的空间）之上，并允许其下的副本世界拥有**自洽的模拟深度**（《惊悚乐园》的真实性），同时通过**分层的治理权限**（《惊悚乐园》的元规则）来管理众创带来的复杂性。
>
> 这正好契合「副本有自主性，但硬框架在主神之中」的核心构想。

## 6. 设计原则

### 6.1 内容永不触碰引擎

> 来源：turn 2

参考 Game Lattice 的架构模式：**C# 提供引擎，JSON 提供灵魂**。引擎核心只是一个对 effect / condition / task 原语的固定解释器；物品、法术、任务、NPC 大脑、天气、经济全部是 JSON 定义，热加载进运行中的 session，不需要重新编译。

对本项目意味着：给社区贡献者提供一个**极低门槛但强约束的剧本 Schema**。

### 6.2 引擎对数值语义无知

见 §2。

### 6.3 核心代码由人类把控

> 来源：turn 2

**Godot 基金会 2026 年 7 月修改贡献政策，禁止 AI 生成的代码进入核心仓库**，理由是：高度依赖 AI 的贡献者未必能理解和修改自己提交的内容。

双向教训：

- 核心引擎部分的代码**应该由人类维护者把控**，能讲清楚每一行为什么存在。
- 社区剧本因为隔离在数据层，风险要小得多。

### 6.4 Spec 先行

> 来源：turn 4

参考 TTA-Solo 的工程纪律：`/specs/` 目录下的 ontology、mechanics、时间线分支规则**必须先于代码存在**。

这正是「主神框架的核心规则应由人类把控、能被讲清楚」的落地方式。

## 7. 技术选型：Unity vs UE5

> 来源：turn 8。**判断：Unity 远比 Unreal Engine 5 更合适。** 原因不在于哪个引擎「更强」，而在于哪个引擎的「性格」与项目核心需求更匹配。

### 7.1 视觉异构是核心需求

- **2D 领域**：Unity 拥有多年打磨的一等公民级工具链（Tilemap、Sprite Shape、2D Physics、2D Lighting）；**UE5 的 2D 能力（通过 Paper2D）对 Epic 而言只是次要关注点**，大多数 UE 的 2D 项目最终不得不自建系统。
- **风格化 3D**：Unity 的 Shader Graph 和 URP 管线能出色完成任务。
- UE5 的视觉天花板确实无可匹敌，但优势集中在**照片级写实或高保真 3D** 上。用一个为 3A 写实而生的引擎去驱动一个 2D 涂鸦关卡，**不仅是巨大的性能浪费，更会因工具链不匹配给社区贡献者带来不必要的门槛**。

### 7.2 众创与快速迭代需要「轻」和「快」

| | Unity | UE5 |
| :--- | :--- | :--- |
| 编辑器体量 | 约 15GB 以上 | 超过 50GB |
| 推荐内存 | 8–16GB RAM | 32GB RAM |
| 启动 | 只需数十秒 | 体感「沉重」 |

> 对于一个需要频繁切换副本、反复调试结算逻辑的框架项目，**启动和编译的每一分钟节省，都会转化为社区贡献的意愿**。

Unity 生态已有 **UnityStarter**（模块化、数据驱动、借鉴 UE GAS 架构）和 **QFramework**（支持 DDD / 事件驱动 / 数据驱动）这类成熟开源框架，可作为「主神」层架构的直接参考或起点。

### 7.3 AI Agent 工具链

- **UE5**：已有强大的 MCP Server 方案，能让 Agent 深度控制编辑器（创建蓝图、搭建关卡、编译 C++），在范围明确的任务上已相当可靠。但属于「**外部工具驱动编辑器**」模式。
- **Unity**：Unity 6 已**内置官方的 AI Assistant 和 MCP Server**，不再是第三方插件，而是引擎原生功能。它被设计为理解实时项目上下文（场景图、GameObject、组件、包），Agent 可直接在编辑器内执行端到端任务。

> 这意味着「Agent 辅助剧本生成」工作流可以更深地与引擎本身融合，而不是依赖外部桥接。

### 7.4 建议的混合架构

**不必把选择看作二选一。**

- **以 Unity 作为「主神框架」的运行时核心和默认呈现层**：负责加载所有 JSON 定义的副本、管理轮回者状态、执行结算逻辑，原生支持 2D 和风格化 3D。其轻量与快速迭代特性，最适合验证最关键的**异构副本切换与结算隔离**。
- **将 UE5 作为「高保真 3D 副本」的可选渲染插件**：对社区中极少数追求顶级 3D 视觉的副本，设计一个接口，让 Unity 端的主神在加载该副本时，将渲染和交互委托给由 UE5 构建的独立场景或模块。**结算清单仍通过统一接口回传。**

> 这既保全了 UE5 的视觉优势，又避免让它承担不擅长的框架核心职责。
>
> **总结**：选择 Unity，赌的是项目「异构、快速、众创」的未来；选择 UE5，赌的是「单一副本的顶级视觉」。对框架的启动阶段，前者的生存概率和迭代速度远高于后者。

## 8. Agent 接入 Unity 的现状

> 来源：turn 10。**结论：可以实现，且不止一种路径。**

### 8.1 DSH（DeepSeek Harness）：社区插件，开箱即用

针对 DSH 有一个专门的社区插件 **dsh-unity-mcp**，安装后即可让 DSH 里的 AI Agent 直接操控 Unity 编辑器。本质上是对开源项目 **mcp-unity** 的封装，内置服务端，零配置，无需手动编辑配置文件。

- 提供 **34 个 Unity 工具**：场景管理、GameObject 增删改查、组件与材质操作、Prefab 管理、菜单执行、测试运行、控制台日志读取等。
- Agent 内调用形式类似 `mcp__unity__create_scene`、`mcp__unity__update_gameobject`。
- 包含**连接诊断**（先探测 Unity 网桥是否在线）和**自动重连**机制。

### 8.2 Codex：Unity 官方插件

Codex 这边是 **Unity 官方直接维护**的插件，定位是让 Codex 使用 Unity 工程师编写的「技能」来工作。它会先检查项目，然后使用当前有效的 API，并在交付结果前进行验证——**有助于规避通用 AI 模型常犯的「使用过时 API」问题**。

- 包含 **31 个由 Unity 各功能团队维护的技能**：UI Toolkit / uGUI、2D 与 Tilemap、URP 与 Shader Graph、音频、导航与物理、多人游戏、Web 与本地化等。
- 提供 `unity-cli` 技能：可在终端安装编辑器版本、创建和打开项目、管理软件包。
- 设置只有两条命令或一键安装，**兼容 Unity 6+**。

### 8.3 通用 MCP 桥接（不绑定特定 Agent）

多个通用 Unity MCP 服务器可让 Claude、Cursor、VS Code Copilot、本地 LLM 等任何兼容 MCP 的客户端控制 Unity：

| 项目 | 工具数 | 备注 |
| :--- | :--- | :--- |
| `CoplayDev/unity-mcp` | 约 50 | 支持 Unity 2021.3 LTS ~ 6.x，MIT，免费 |
| `AnkleBreaker-Studio/unity-mcp-plugin` | 268 | 覆盖场景、GameObject、组件、构建、性能分析、Shader Graph、地形、物理、NavMesh 等，免费开源 |
| `sebastiankurvers-dev/agent-bridge-for-unity` | 243 | 包括场景搭建、视觉 QA、Play Mode 控制等 |

> Unity 官方的 MCP 服务器包含在 AI Assistant 包中，**需要 Unity 6 及有效订阅**。社区方案大多不依赖官方订阅，兼容范围更广。

### 8.4 能力边界与风险（三条）

1. **Unity 服务条款对 AI 接入有框架性要求**：2026 年 6 月更新的 ToS 规定，AI agents、LLM 和 MCP 客户端/服务器**只能通过 Unity 运营或指定的框架与平台交互**。
   > 如果项目要长期维护，**优先选择 Unity 官方认可的 MCP 路径**（官方插件或官方 MCP 服务器）会更稳妥，社区 MCP 方案在合规上存在不确定性。
2. **Agent 的控制能力是「编辑器操作层」的，不是「游戏逻辑层」的**：它们可以创建场景、修改组件、编辑 C# 脚本、运行测试，但**「主神结算逻辑」和「异构副本 Schema」仍需要由人类设计和实现**。Agent 擅长的是把已经想清楚的结构快速搭建出来，而不是替你决定这个结构应该长什么样。
3. **部分操作存在风险**：有分析指出，Unity MCP 工具中相当一部分具备修改或销毁数据的能力，一些破坏性工具没有内置限制。
   > 在众创项目中，如果让 Agent 直接对主神账本相关的场景或脚本进行操作，**建议在 CI 或权限层面加入写操作限制**，避免 Agent 在循环中意外触发批量修改。

### 8.5 对项目的务实含义

> Agent 可控的 Unity 正好可以用来加速框架本身的脚手架搭建和副本模板生成。可以用 DSH 或 Codex 驱动 Unity，快速创建「3D 小房间战斗副本」和「2D 生存副本」的场景骨架、组件配置和测试脚本，然后由人类维护者审核和固化这些模板。
>
> **Agent 负责「搭」，人负责「定规则」和「守结算边界」**——这与分层架构一致。

## 9. GitHub 同构项目参考

> 来源：turn 4。**结论：不存在**同时具备「3D 呈现 + 主神规则引擎 + JSON 剧本众创」的完整雏形。但每一块拼图都有现成项目可参考。

### 路线一：无限流「文字版」规则引擎 —— 最接近「主神」层

| 项目 | 特点 |
| :--- | :--- |
| **AI Universe Simulator**（`felixQAQ-edu/ai-universe-simulator`） | 最接近「主神框架 + 副本注册」机制。引擎对数值语义无知，只遍历 `attributes` 字典做通用结算；各世界共用「世界生成 → 角色/属性 → 规则矩阵 → 动态事件流 → 多结局收敛」管线；加一个新世界只需后端一条元数据 + 前端一行联合类型。其 **ADR-008** 正是为多模式扩展设计 |
| **TTA-Solo**（`theinterneti/tta-solo`） | 自称 AI-Native Infinite Multiverse Engine，神经符号架构：LLM 负责叙事与即兴，Python 负责 SRD 5e 规则、骰子和状态验证，无状态 Skills 做意图翻译。**Spec 先行** |
| **`dew`**（`Liu26609/dew`） | 基于《无限恐怖》蓝本的主神空间文字 RPG 插件，直接对应「轮回者—兑换—副本」循环，但架构深度有限 |

### 路线二：JSON 数据驱动的通用框架 —— 最接近「剧本封装」层

| 项目 | 特点 |
| :--- | :--- |
| **Game Lattice**（`Toxic-Cookie/game-lattice`） | 这一层最成熟的参考。**内容永不触碰 C#**，且**LLM 可写**；提供 `docs/llm-guide.md`；为每种 def kind 生成 JSON Schema，带 validation CLI 做链接检查和可达性警告 |
| **pgrpg** | ECS + JSON / YAML 定义 AI、场景、处理器 |
| **BiC Game Systems** | TypeScript、JSON-first 定义 stats / quests / factions |
| **EVEngine** | RPG 模块：属性名、效果 ID 全部用字符串而非编译期枚举（见 §2） |

### 路线三：AI Agent 生成 3D 游戏 —— 有工具，但无无限流语义

| 项目 | 特点 |
| :--- | :--- |
| **UniGen**（`github.com/yxwan123/UniGen`） | 端到端多智能体框架：Planning / Generation / Automation / Debugging 四个 Agent，在 Unity / Unreal 上从自然语言生成可运行 3D 游戏，**降低开发延迟 91.4%** |
| **AutoUE** | 检索增强生成把 UE 工具文档喂给 Agent，配合自动化 play-testing 管线 |
| **GameFactory-3A** | 覆盖图片、3D 资产、动作、音频到 UE5 / Blender / Unity / Godot / three.js 的生成管线 |
| **Code2Games** | 从场景规划、元素放置、资产实例化到 gameplay logic 分阶段交给 Agent，接入 Blender 和 Hunyuan3D |

> 共同信号：**Agent 的产出是「项目骨架 + 可运行原型」，不是成品游戏。** 仓库里真正需要沉淀的是框架代码、场景模板、交互契约，而不是让每个贡献者都从零跑一遍 Agent。

### 缺失的那一块

把三条路线拼起来，缺失的恰好是最核心的部分：**一个能让社区贡献者用 JSON 定义「3D / 异构副本」的接口层**。

- AI Universe Simulator 证明了无限流规则可以数据驱动，但停留在文字。
- Game Lattice 证明了 JSON 可以驱动复杂 RPG 内容，但不内置无限流。
- UniGen 能生成 3D，但不理解「轮回」和「副本」的语义。

### 对「缝合」题材的现实提醒

> 来源：turn 2

无限流「缝合」的天然属性意味着剧本会大量引用已有的 ACG / 影视世界观。**框架开源不等于可以随意分发受版权保护的角色、场景和剧情文本。**

比较安全的做法：剧本以「原创副本」或「公共领域 / 授权明确的世界观」为主，同人性质的副本放在**显式标记的社区内容池**中，并保留 takedown 通道。

### 合规风险

> 来源：turn 2

AI 生成内容在中国的游戏语境下，**著作权归属和训练数据供应链**是已经进入司法和行业讨论的现实风险。

- 如果框架用 Agent 生成场景资产或剧本草稿，至少需要在贡献协议中明确：**贡献者对其提交的 AI 辅助生成内容负责，项目方保留移除的权利**。
- 如果 Agent 调用了第三方模型或资产服务，**训练数据的合规性会沿着供应链传导到最终游戏**——这一点需要在 README 里说清楚，而不是等到有人来主张权利时才处理。

## 10. 落地顺序

> 来源：turn 2

### 第一步：不要先做 3D

先用 Game Lattice 式的数据驱动思路，在一个 2D 或极简 3D 原型里把「**主神规则引擎 + JSON 副本加载 + 结算循环**」跑通。

跑通之后，「在副本里加一张桌子还是加一座城堡」只是资产和场景复杂度的问题。

### 第二步：把 Schema 和 validation CLI 做扎实

这是社区众创的命门。**一个贡献者能否在不读引擎代码的情况下写出一个可被正确加载和结算的副本，决定了项目是「众创」还是「少数程序员的私享框架」。**

### 第三步：Agent 用在降低贡献摩擦上，而不是替代贡献者

提供一个 Agent 辅助的剧本草稿生成器：贡献者输入副本梗概，Agent 按 Schema 产出初稿，然后由人类修改、提 PR。

这样 Agent 的产出停留在**贡献者的本地草稿**，不直接进入仓库——既利用了效率，又避开了「AI slop 涌入核心」的问题。

### 第四步：先建治理文档，再开 PR

贡献指南、Schema 文档、审核标准、行为准则、版权 / takedown 政策——这些看起来不「3D」，但它们决定了开源众创项目能不能活过前一百个 PR。

### 最小验证方案

> 来源：turn 6

第一版**不需要**同时支持 3D、2D 和涂鸦。先做最简的异构验证：

- 副本 A：「3D 小房间里的战斗」，用 `{hp, atk, def}`
- 副本 B：「2D 平面上的生存」，用 `{health, hunger}`
- 两者通过**同一个主神结算接口**提交清单，主神把结果映射到同一套兑换点

> **只要这两个异构副本能无缝切换且主神账本不被污染，架构就验证通过了。**

## 11. 剧本封装的字段草案

> 来源：turn 2。这是对话中给出的**初步字段草案**，不是最终 Schema。

```
副本 ID / 名称 / 难度等级
入场条件（轮回者最低属性 / 携带物品限制）
场景列表（引用框架的场景模板或资产 ID）
事件节点（触发条件 → 效果 → 下一个节点）
任务目标（主任务 + 可选支线，判定谓词用统一词汇表）
奖励表（兑换点 / 物品 / 能力，引用主神词汇表）
失败结算（永久死亡？扣除？强制退出？）
```

只要 Schema 稳定，贡献者可以只写 JSON / YAML，甚至让 LLM 辅助生成符合 Schema 的剧本草稿，然后提交 PR。
