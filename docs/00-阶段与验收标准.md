## 0. 什么样的标准才算合格（元标准）

### 0.1 验收项六字段，缺一即无效

| 字段 | 要求 | 不合格示例 |
| :--- | :--- | :--- |
| **ID** | 全局唯一，格式 `S<阶段>-G<关卡>-<序号>` | 「属性轴测试」 |
| **类型** | `硬` / `观察`，二选一 | 「重要」 |
| **输入 / 前置** | 引用 §1 夹具 ID；无夹具时写明具体文件、配置、命令 | 「准备两个副本」 |
| **期望结果** | 可机器断言：退出码、深度相等、命中数、哈希、枚举值、字段存在性 | 「互不干扰」「合理」「可读」 |
| **证据路径** | `evidence/<stage>/<ID>.<ext>`，写清文件内容 | 「保留记录」 |
| **失败判据** | 期望结果中任一条件不满足即 FAIL | 缺失 |

### 0.2 禁用词表

验收项的「期望结果」列出现下列词，该条即判为**无效验收项**，必须改写为可断言形式：

`或`（表示二选一路径）／ `互不干扰` ／ `合理` ／ `可读` ／ `真实使用过` ／ `已确认` ／ `评审通过` ／ `文档写完` ／ `校验过一次` ／ `基本` ／ `尽量` ／ `视情况` ／ `失败或被拦截`。

> 允许多条并列条件，但必须用 `且` 连接，每条各自可判定。

### 0.3 判定值定义

| 值 | 含义 | 能否用于硬门槛 |
| :--- | :--- | :--- |
| `PASS` | 期望结果全部满足，证据文件已生成且内容非空 | 是 |
| `FAIL` | 任一条件不满足 | 是 |
| `BLOCKED` | 依赖的上游配置（`config/*`）尚未定稿，期望值无法写出 | 是（**阶段不得退出**） |
| `N/A` | 经书面说明本阶段不适用，且判定人签字 | **否**，硬门槛不得标 N/A |

**禁止**把 `BLOCKED` 记为 `PASS`，也**禁止**在 S0 未定稿时手写玩法数值充当期望值（见 §0.5）。

### 0.4 阶段退出判据

一个阶段可进入下一阶段，当且仅当：

1. `python gates/check.py --stage <sN>` 退出码 = 0（见 §0.7）；该命令同时检查测试文件齐备与 `pending` 清零；
2. 该阶段全部 `硬` 项由测试套件判为 `PASS`（`BLOCKED` / `pending` 计为未通过）；
3. 全部 `观察` 项已记录判定结果，`FAIL` 不阻塞但必须写入验收记录；
4. 判定人**不是**该阶段的实现者（隔离复核，可以是隔离上下文的 agent，须在记录中写明模拟方式）；
5. `evidence/<stage>/summary.md` 由测试产物汇总生成，含每项 ID、判定、证据路径、判定日期；不手工填写判定值。

### 0.5 数值约定（防止验收标准偷渡规则）

- 验收断言**不得硬编码玩法数值**。凡涉及阶位区间、系数、惩罚额、时间单位，一律引用 `config/<name>` 中 S0 / S3 定稿的值，断言写作「与 `config/<name>` 的键值一致」。
- 配置未定稿时，该项标 `BLOCKED`，**不得编造期望值**。
- 本文件所有 `<占位符>` 由 S0 定稿后替换，替换动作本身记入 S0 验收记录。
- 夹具中的数值仅用于**结构测试**（如「整数」「非空」「去重」），不代表玩法设定。

### 0.6 被测对象术语（验收时的边界）

| 术语 | 定义 | 验收时的可观测形式 |
| :--- | :--- | :--- |
| **账本** | 主神持有的轮回者永久状态 | 序列化为 `ledger.json`，字段集由 S0 的「结算清单」契约确定；比对其哈希与深度相等 |
| **结算清单** | 副本提交给 `settle()` 的标准结构 | §1 F4 的 JSON 实例；字段级校验 |
| **引擎核心** | 目录 `<engine-core>/`，由 S0 登记路径 | 目录路径写入 `config/paths.json`；diff / 静态扫描以此为范围 |
| **状态快照** | 入场时冻结的账本副本 | `snapshot.json`，与入场前 `ledger.json` 深度相等 |
| **渲染层** | 读取 `render_profile` 并切换呈现的模块 | 加载日志中 `render_profile=<值>` 的行 |
| **直写** | 副本代码绕过 `settle()` 修改账本的任何尝试 | §1 F6 恶意副本的固定行为 |

### 0.7 判定权归属：测试先行

**本文件的验收表格降级为人类可读索引，不再是判据。** 判定依据是 `gates/manifest.json`，由 `gates/check.py` 消费：

```
python gates/check.py --stage s1
```

**退出码即判定**：`0` = 该阶段可退出，`1` = 不可退出。人不再填写 `PASS` / `FAIL`；`evidence/*` 是测试产出的日志，不是人工判定表。

| 层 | 能否测试先行 | 处理方式 | 硬门槛数 |
| :--- | :--- | :--- | :--- |
| `invariant` | 能，且不依赖玩法数值 | 实现之前先写测试，当前应为红 | 32 |
| `config_driven` | 能写骨架，不能写死期望值 | 断言引用 `config/*`；配置定稿后把 manifest 中该 Gate 的 `status` 从 `pending` 改为 `active` 即激活 | 17 |
| `human_in_loop` | 不能全自动化 | 机器留痕 + 人工签字，不参与自动退出码；证据文件缺失时该 Gate 记 `FAIL` | 6 |

**两条硬规则**

1. `pending` 是**未激活**，不是 `skip`。`pending_count > 0` 时阶段不得退出（`check.py` 返回 1）。禁止通过删除条目、把 `pending` 直接改成 `active`、或伪造期望值把红变绿。
2. **测试代码本身必须被 review**：合入前执行变异验证——故意破坏被测实现，对应测试必须从绿变红，证据写入 `evidence/<stage>/mutation.log`。测试先行把信任从「验收人」转移到「测试代码」，这一环不能省。

**门禁工具链与运行时解耦**：`check.py` 只用 Python 标准库，不需要等技术栈拍板（Q1）。但 `gates/tests/*.py` 的 runner 依赖运行时技术栈；Q1 未定时 S1 的测试文件无法编写，门禁自然保持 `DENIED`。这使 Q1 成为 S0 的**事实硬前置**，无需新增验收项。

**历史状态（2026-11-12，门禁初建时的红阶段；当前实测见文末 §13.15）**：

```
全量:    hard_tests=55  pending=17  missing_active_files=38   GATE_EXIT: DENIED (1)
--stage s1: hard_tests=11  pending=0   missing_active_files=11   GATE_EXIT: DENIED (1)
```

S1 的 11 项全部是 `invariant`、`pending=0`，只缺测试文件——**这是 TDD 的正确起点，不是失败**。

**总览表说明**：S0~S4 是时间视角；SC / SI 是**跨阶段套件**，不排在串行序列里，由 `check.py --stage sc` / `--stage si` 独立运行。

**拆分理由**：S3 原本把 7 块规则塞进一个阶段，任意一块失败即整阶段停摆。拆成 6 个独立 Gate 后，可逐项 PASS，未通过的 Gate 单独标 `BLOCKED` 并回填规则，不影响其余 Gate。

**关键性质**：S1 的全部 11 个硬门槛**不引用任何玩法数值**（仅用 F1~F6 的结构值），因此 S0 完成后可立即启动，无需等待 S3 的规则定稿。

## 12. 并行研发契约（真正的目标）

> **发起人的最终目的**：先拟定全部指向最终结果的刚性测试，再放手让多 agent 并行研发，既不跑偏、也不走走停停。
> 本节是该目标下的**判据**。S0~S4 是时间视角（进度用），P1~P7 是并行视角（分工用），两者并存，但**「能不能放手」只由本节决定**。

### 12.1 视角错配（必须先承认）

S0→S4 是**串行**阶段门禁，为单人顺序推进设计；并行研发按**架构边界**切分，各包同时开工。若以阶段门禁作为并行开发的推进节奏，必然走走停停。因此：

- 阶段表格降级为进度视图，不作为 agent 的任务队列；
- agent 的任务单元是 **P1~P7 工作包**，每个包自带契约测试，可独立跑绿；

### 12.5 端到端黄金链路 G1（指向最终结果）

**骨架已落成 `gates/tests/c30-01.py`（八步断言规格写在文件 docstring），当前为红**：

```
F3 初始账本
  -> 入场公证（属性轴校验 / 资产 ID 在库 / 冻结快照）
  -> 加载副本 A（{hp, atk, def}），触发事件
  -> 副本内死亡或完成 -> 生成结算清单
  -> settle() 落账（兑换点 / 能力 ID / 物品 ID 均来自词汇表）

  -> 再结算 -> 最终账本与按契约手算的期望值深度相等
```

**断言**：全程账本只被 `settle()` 改动；A 的属性轴不出现在 B 的快照里；跨副本带出的能力在 B 中按词汇表生效；最终账本逐字段可复算。**这条测试绿了，才谈得上"架构跑通"**，阶段门禁全绿不算。

1. `gaps = 0`：所有架构契约都有测试，无空白；

## 13. 审查结论：跨阶段与融合层（2026-11-12）

### 13.1 审查发现的结构性缺口

审查「大阶段 / 小阶段 / 测试与目标 / 跨阶段 / 融合」五问后，确认三处结构性问题：

1. **大阶段没有阶段级验收**。§0.4 的阶段退出只是「下属 Gate 全部 PASS」的**聚合**，不是一条独立断言。没有任何测试问「S1 结束时架构契约是否整体成立」，也没有阶段出口的状态契约。
