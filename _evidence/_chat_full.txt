===== [turn 2] ASSISTANT =====
你的设想在技术上是可行的，但需要把“让 AI Agent 做游戏”和“让社区填充剧本”拆成两个不同层面的问题来处理。AI Agent 适合做“框架的脚手架”和“单次运行的导演”，但不适合直接生成一个可长期众创的 3D 游戏底座；而“主神框架开源、社区众创剧本”的真正难点不在 3D 渲染，在内容封装的规范和治理机制。

### 一条被验证过的 Agent 路径：多智能体“零代码”管线
2026 年的研究已经给出了比较清晰的范式。UniGen 是一个端到端多智能体框架，把自然语言需求拆成四个 Agent：Planning Agent 生成结构化蓝图，Generation Agent 产出可执行的 C# 脚本，Automation Agent 做组件绑定和场景搭建，Debugging Agent 做实时纠错，在 Unity/Unreal 上把开发延迟降低了 91.4%。AutoUE 走的是另一条路：用检索增强生成把 UE 工具文档喂给 Agent，再配合自动化 play-testing 管线，让生成出来的关卡和交互逻辑真的能跑起来、能被测试。Code2Games 则把范围进一步拆细，从场景规划、元素放置、资产实例化到 gameplay logic 分阶段交给 Agent 处理，并且接入了 Blender 和 Hunyuan3D 做资产生成。-1-3
这些工作的共同信号是：Agent 的产出是“项目骨架 + 可运行原型”，不是成品游戏。你的 GitHub 仓库里真正需要沉淀的，是 Agent 生成出来的框架代码、场景模板、交互契约，而不是让每个贡献者都从零跑一遍 Agent。

### “主神”应该做成什么：规则引擎，而不是剧本本身
无限流的核心机制在设定层面已经非常清晰：强制任务、兑换强化、时空穿越，构成“主神空间—轮回者—副本世界”的三位一体框架。对应到游戏架构上，“主神”应该是一个规则与状态管理引擎，负责：
- 轮回者状态：属性、技能、兑换点、装备、永久死亡标记；

- 副本准入与结算：任务生成、完成条件判定、奖励发放、失败惩罚；

- 跨副本持久化：从 A 副本带出的能力如何在 B 副本中生效（或失效）；

- 兑换系统：用统一的数值词汇表定义“血统、功法、道具”的 cost 与 effect。

社区贡献的剧本，应该只描述“这个副本里有什么、会发生什么”，不触碰主神的规则实现。否则每个剧本都自带一套私有规则，框架会迅速失控。

### 剧本封装：用“数据定义”把贡献者和引擎隔开
Game Lattice 的做法值得直接借鉴：C# 核心只是一个固定的解释器，物品、法术、任务、NPC 大脑、天气、经济全部是 JSON 定义，热加载进运行中的 session，不需要重新编译。它的数据格式被设计成“LLM 和人类都能写”，并且为每种 def kind 生成了 JSON schema，还带一个 validation CLI 做链接检查和可达性警告。-22
对你的项目来说，这意味着可以给社区贡献者提供一个极低门槛但强约束的剧本 schema。一个副本剧本大致需要这些字段：
副本 ID / 名称 / 难度等级
入场条件（轮回者最低属性 / 携带物品限制）
场景列表（引用框架的场景模板或资产 ID）
事件节点（触发条件 → 效果 → 下一个节点）
任务目标（主任务 + 可选支线，判定谓词用统一词汇表）
奖励表（兑换点 / 物品 / 能力，引用主神词汇表）
失败结算（永久死亡？扣除？强制退出？）
只要 schema 稳定，贡献者可以只写 JSON/YAML，甚至让 LLM 辅助生成符合 schema 的剧本草稿，然后提交 PR。Godot 2026 年 7 月修改贡献政策、禁止 AI 生成的代码进入核心仓库，给出的理由很直接：高度依赖 AI 的贡献者未必能理解和修改自己提交的内容。这个教训对你是双向的：如果你用 Agent 生成框架代码，核心引擎部分的代码应该由人类维护者把控、能讲清楚每一行为什么存在；而社区剧本因为隔离在数据层，风险要小得多。

### 开源治理：区分“核心”和“内容”，用不同的规则
SandNet 的 AGPL-3.0 加模块化架构、允许社区 self-host 和 extend，适合“防止被闭源 fork 后收割”的场景。Project N.E.K.O. 则采取 Open Core + MIT：AI 逻辑、UGC 接口、基础交互永久 MIT，闭源部分只放在付费内容和增值服务上。对你的“主神框架”来说，一个现实的组合是：-9
- 框架核心（规则引擎、schema、加载器）：MIT 或 Apache 2.0，降低贡献门槛；

- 官方内容包 / 内置副本：可以更严格，比如 CC BY-SA 或保留部分权利，防止有人直接把官方内容打包卖；

- 贡献流程：schema validation CI → 人类 review → 合入。Godot 基金会要求 PR 必须经过维护者人工审批，即使是 MIT 项目也保留这条线。你的项目需要类似机制：自动校验 schema 合规性，人类判断剧本质量与世界观一致性。

另外，无限流“缝合”的天然属性意味着剧本会大量引用已有的 ACG / 影视世界观。框架开源不等于可以随意分发受版权保护的角色、场景和剧情文本。比较安全的做法是：剧本以“原创副本”或“公共领域/授权明确的世界观”为主，同人性质的副本放在一个显式标记的社区内容池中，并保留 takedown 通道。

### 合规上需要提前正视的两个问题
AI 生成内容在中国的游戏语境下，著作权归属和训练数据供应链是已经进入司法和行业讨论的现实风险。2026 年的多个法律论坛和行业回顾都在讨论 AI 生成美术、声音、文本的作品认定与侵权认定。如果你的框架用 Agent 生成场景资产或剧本草稿，至少需要在贡献协议中明确：贡献者对其提交的 AI 辅助生成内容负责，项目方保留移除的权利。同时，如果 Agent 调用了第三方模型或资产服务，训练数据的合规性会沿着供应链传导到最终游戏，这一点需要在 README 里说清楚，而不是等到有人来主张权利时才处理。

### 一个务实的落地顺序
第一步，不要先做 3D。先用 Game Lattice 式的数据驱动思路，在一个 2D 或极简 3D 原型里把“主神规则引擎 + JSON 副本加载 + 结算循环”跑通。跑通之后，“在副本里加一张桌子还是加一座城堡”只是资产和场景复杂度的问题。
第二步，把 schema 和 validation CLI 做扎实。这是社区众创的命门。一个贡献者能否在不读引擎代码的情况下写出一个可被正确加载和结算的副本，决定了你的项目是“众创”还是“少数程序员的私享框架”。
第三步，Agent 用在“降低贡献摩擦”上，而不是“替代贡献者”。可以提供一个 Agent 辅助的剧本草稿生成器：贡献者输入副本梗概，Agent 按 schema 产出初稿，然后由人类修改、提 PR。这样 Agent 的产出停留在贡献者的本地草稿，不直接进入仓库，既利用了效率，又避开了 Godot 式“AI slop 涌入核心”的问题。
第四步，先建治理文档，再开 PR。贡献指南、schema 文档、审核标准、行为准则、版权/takedown 政策——这些看起来不“3D”，但它们决定了一个开源众创项目能不能活过前一百个 PR。

### 路线一：无限流“文字版”规则引擎——最接近你的“主神”层
这类项目已经跑通了“无限流语义 + 数据驱动 + 结构化输出”的闭环，只是呈现形式停留在文字/2D，没有 3D。
最值得细看的是 AI Universe Simulator（felixQAQ-edu/ai-universe-simulator）。它的架构思路和你“主神作为规则层、剧本作为数据层”的设想高度同构：引擎对数值语义无知，只遍历 attributes 字典做通用结算，不认识任何一根轴的名字；各个世界（规则怪谈、末日生存、修仙、克苏鲁等）共用同一条“世界生成 → 角色/属性 → 规则矩阵 → 动态事件流 → 多结局收敛”的管线，加一个新世界只需要后端一条元数据 + 前端一行联合类型。这几乎就是你想要的“主神框架 + 副本注册”机制的雏形，只是它的“副本”是文字世界，不是 3D 场景。
另一个可以参考的是 TTA-Solo（theinterneti/tta-solo），它把自己定位为“AI-Native Infinite Multiverse Engine”，采用神经符号架构：LLM 负责叙事和即兴，Python 负责 SRD 5e 规则、骰子和状态验证，中间用无状态 Skills 做意图翻译。它的工程纪律也值得注意——Spec 先行，/specs/ 目录下的 ontology、mechanics、multiverse 时间线分支规则必须先于代码存在。这对应你“主神框架的核心规则应由人类把控、能被讲清楚”的需求。
此外还有 dew（Liu26609/dew），一个基于《无限恐怖》蓝本的主神空间文字 RPG 插件，功能上直接对应“轮回者—兑换—副本”循环，但定位是聊天平台插件，架构深度有限。

### 路线二：JSON 数据驱动的通用游戏框架——最接近你的“剧本封装”层
Game Lattice（Toxic-Cookie/game-lattice）是这一层最成熟的参考。它的核心设计一句话就能概括：C# 是引擎，JSON 是灵魂。C# 核心只是一个对 effect/condition/task 原语的固定解释器；物品、法术、任务、NPC 大脑、天气、经济全部是 JSON def，热加载进运行中的 session，不需要重新编译。它的数据格式被明确设计为“LLM 和人类都能写”，并且提供了 docs/llm-guide.md，把这份指南塞进模型上下文，模型就能写出可运行的内容。-39
这几乎就是你“社区用 JSON 写副本、引擎只负责加载和结算”这一设想的直接技术参照。Game Lattice 本身是 RPG 框架，不内置无限流语义，但它的架构模式可以被你的“主神”层直接借用——把轮回者属性、兑换点、副本准入、永久死亡标记定义为 JSON def，把副本事件节点和结算谓词也用同一套原语表达。
类似思路的还有 pgrpg（ECS + JSON/YAML 定义 AI、场景、处理器）、BiC Game Systems（TypeScript、JSON-first 定义 stats/quests/factions）等，但 Game Lattice 在“内容永不触碰 C#”和“LLM 可写”这两点上走得最远。

### 路线三：AI Agent 生成 3D 游戏——有工具，但尚未与无限流语义结合
如果你坚持 3D，这一层有可用的 Agent 脚手架，但它们生成的是通用 3D 游戏，不包含“主神—轮回者—副本”的规则语义。
UniGen 是一个端到端多智能体框架，用 Planning、Generation、Automation、Debugging 四个 Agent 在 Unity/Unreal 上从自然语言生成可运行的 3D 游戏，代码和 prompt 模板在 github.com/yxwan123/UniGen。GameFactory-3A 覆盖图片、3D 资产、动作、音频到 UE5/Blender/Unity/Godot/three.js 的生成管线。AutoUE 则专门针对 Unreal Engine，用多智能体加自动化 play-testing 管线。
你可以用这些工具生成 3D 资产和场景模板，但“这个场景属于哪个副本、进入条件是什么、完成后结算什么奖励”——这些无限流语义必须由你自己的“主神”数据层来定义。换句话说，Agent 生成的是“副本里的东西”，不是“副本在无限流框架中的位置”。

### 一个值得注意的空白：没有一个项目在做“3D 场景模板 ↔ 主神规则”的接口
把上面三层拼起来看，缺失的恰好是你设想中最核心的那一块：一个能让社区贡献者用 JSON 定义“3D 副本”的接口层。AI Universe Simulator 证明了无限流规则可以数据驱动，但它停留在文字；Game Lattice 证明了 JSON 可以驱动复杂 RPG 内容，但它不内置无限流；UniGen 能生成 3D，但不理解“轮回”和“副本”的语义。
这意味着你的项目如果启动，第一优先级不是 3D，而是定义那个接口：一个 3D 副本的 JSON schema 长什么样——它引用哪些场景资产 ID、事件节点如何与 3D 触发器绑定、结算谓词如何调用主神引擎的轮回者状态。这个 schema 一旦稳定，Game Lattice 式的加载器和 UniGen 式的生成管线都可以作为实现参考接进来。GitHub 上没有现成的完整答案，但每一块积木都已经摆在那里了。

### 核心机制：引擎对数值“语义无知”，副本自己定义属性
你举的“生存副本只有健康和饥饿，战斗副本有力敏体智”，在工程上已经有直接对应的架构模式。AI Universe Simulator 的 ADR-008 就是为此设计的：引擎的核心是一个开放字典 attributes，它遍历所有 key 做通用结算，但不关心 key 叫什么、代表什么。规则怪谈模式用 {hp, san}，末日生存模式用 {hp, hunger}，引擎完全兼容——加一个新副本类型，只需要一条“元数据”声明这个副本有哪些数值轴，不需要改引擎核心。-20
这正好对应你说的“副本有自主性，但硬框架在主神之中”：属性名称和属性含义由副本定义，但属性的存储格式、更新方式和边界规则（比如数值范围 0–100）由主神引擎统一持有。副本可以在自己的沙盒里跑一套完全不同的属性系统，结算时把结果映射回主神账本即可。
EVEngine 的 RPG 模块也遵循同一原则：属性名、效果 ID 全部使用字符串而非编译期枚举，新增一个属性不需要改引擎头文件、不需要重新编译，数据可以完全放进 JSON 由策划配置。这意味着社区贡献者写一个新副本时，声明自己的属性集就像写一行配置，而不是提交一段代码。-12

### 视觉层：3D / 2D / 涂鸦的切换，是“管线切换”，不是“引擎重写”
你设想的“上一个副本 3D，下一个 2D 平面，再下一个涂鸦风格”，在渲染层面是成熟的。Unity 的运行时管线切换方案以渲染契约抽象为底座，可以根据场景需要实时切换写实渲染、风格化渲染等不同管线，而不必重构底层逻辑。Godot 的架构模式也天然支持这一点：每个场景可以拥有独立的视觉表现，而全局状态通过 AutoLoad 单例或共享状态插件跨场景保持，场景切换时只替换呈现层，不触碰数据层。-33
关键是把“视觉风格”也做成副本元数据的一部分。主神引擎在加载副本时读取 render_profile: "3d" | "2d_flat" | "graffiti"，然后把渲染权交给对应的管线；主神自身不知道也不关心这个副本长什么样，它只负责在结算时从副本接口拉取收益数据。

### 收益转换：主神是唯一的“账本”，副本只是“临时工作区”
这是你设想中最关键的一环，也是最容易失控的地方。如果允许每个副本随意定义属性和玩法，那么“副本结束时把收益按主神规则转换”就必须有一个严格的隔离边界。
一个可行的设计是：副本内部的一切（积分、道具、临时能力、甚至角色死亡）都是副本沙盒内的局部状态，不直接写入主神账本。副本结束时，只向主神提交一份标准化的结算清单：
副本 ID / 轮回者 ID / 完成状态
兑换点增量（整数）
永久性能力变更（引用主神词汇表的 ID 列表）
携带出副本的物品（引用主神物品表的 ID 列表）
主神收到这份清单后，用自己的规则做转换和落账。副本作者不需要知道主神空间的兑换汇率，他只需要按 schema 填写“这个副本产出了什么”；汇率、稀有度映射、跨副本平衡性调整，全部由主神层的维护者控制。这样，副本的“自主性”止步于结算接口，主神的“硬框架”体现在接口背后的计算规则上。
Steam 上的《主神的游戏》已经商业验证了这个模式：九个世界各有完全独立的规则、战斗方式和通关思路，但完成后统一回到主神空间，用技能芯片和血统进行跨副本的永久成长。它的“收益转换”不是把副本内的数值直接搬出来，而是把副本内的成就抽象成主神空间可识别的成长货币。

### 真正的工程难点：不是“切换”，是“切换后的状态隔离”
架构上把“副本沙盒”和“主神账本”分开之后，最需要守住的纪律是：副本永远不能直接写主神状态。副本可以读取进入时的快照（轮回者当前属性、携带物品），但它的所有修改都发生在自己的局部状态里；只有主神收到结算清单后，才执行一次性的、经过校验的写入。
这对应分布式系统中的快照隔离模式：一个操作在它的一致性快照中执行，外部看不到中间状态，只有在提交时才一次性生效。Godot 的全局状态插件和跨引擎状态同步专利都采用了类似思路——持久状态由权威层持有，场景层只做临时呈现和局部交互。-33
你不需要一开始就做分布式系统那么重的实现。一个简单的规则就够了：主神的 settle(副本结算清单) 是唯一能修改轮回者永久状态的入口，副本代码和副本数据在任何情况下都不能直接操作这个入口之外的主神状态。

### 一个务实的起点
第一版不需要同时支持 3D、2D 和涂鸦。先做一个最简的异构验证：两个副本，一个是“3D 小房间里的战斗”，用 {hp, atk, def}；另一个是“2D 平面上的生存”，用 {health, hunger}。两者通过同一个主神结算接口提交清单，主神把结果映射到同一套兑换点上。只要这两个异构副本能无缝切换且主神账本不被污染，你的架构就验证通过了。之后加涂鸦风格、加更多属性轴，都是在已经稳定的接口上追加配置，而不是重新设计。

### 🎨 视觉异构是你的核心需求，而 Unity 在这方面是明确的强者

UE5 的视觉天花板确实无可匹敌，但它的优势集中在照片级写实或高保真 3D 上。用一个为 3A 写实而生的引擎去驱动一个 2D 涂鸦关卡，不仅是一种巨大的性能浪费，更会因为工具链的不匹配而给社区贡献者带来不必要的门槛。-1

### ⚡ 众创与快速迭代，需要的是“轻”和“快”
你的项目本质是一个框架，成败取决于社区贡献者（包括你自己作为原型验证者）填充内容的效率。在这个维度上，两个引擎的体验差异巨大。
Unity 的编辑器体量显著更轻（约 15GB 以上，推荐 8-16GB RAM），启动只需数十秒，在小团队和移动/独立游戏管线上迭代速度通常更快。相比之下，UE5 编辑器超过 50GB，推荐 32GB RAM，体感“沉重”。对于一个需要频繁切换副本、反复调试结算逻辑的框架项目，启动和编译的每一分钟节省，都会转化为社区贡献的意愿。
更重要的是，Unity 拥有庞大且极其成熟的社区和生态，几乎所有你能想到的问题都有现成的论坛、教程和开源框架。对于众创项目而言，这意味着当贡献者遇到问题时，解决问题的摩擦更低。Unity 生态中已有像 UnityStarter（模块化、数据驱动、借鉴 UE GAS 架构）和 QFramework（支持 DDD/事件驱动/数据驱动）这样成熟的开源框架，可以作为你“主神”层架构的直接参考或起点。

### 🤖 AI Agent 工具链：两者都有，但 Unity 的集成更“原生”
既然你的开发流程深度依赖 Agent，引擎对 Agent 的支持方式就至关重要。
UE5 生态中已有强大的 MCP Server 方案，能让 AI Agent 深度控制编辑器，执行创建蓝图、搭建关卡、编译 C++ 等操作，并且有真实的项目反馈表明，在范围明确的任务（如创建角色蓝图、配置组件、编写样板代码）上 Agent 已经相当可靠。但 UE 的 Agent 方案更多是“外部工具驱动编辑器”的模式。-19
Unity 则走得更远一步。Unity 6 已内置了官方的 AI Assistant 和 MCP Server，这不再是第三方插件，而是引擎的原生功能。它被设计为理解你的实时项目上下文（场景图、GameObject、组件、包），Agent 可以直接在编辑器内执行端到端任务：编写 C# 脚本、修改场景组件、创建 Prefab 并验证行为。这意味着你的“Agent 辅助剧本生成”工作流可以更深地与引擎本身融合，而不是依赖外部桥接。-27

### 💎 一个更现实的混合架构：以 Unity 为核心，按需接入 UE5
完全不必把选择看作二选一。一个更符合你“主神”分层理念的架构是：
以 Unity 作为“主神框架”的运行时核心和默认呈现层。它负责加载所有 JSON 定义的副本、管理轮回者状态、执行结算逻辑，并原生支持 2D 和风格化 3D 副本。它的轻量和快速迭代特性，最适合用来验证你最关键的业务逻辑——异构副本的切换与结算隔离。
将 UE5 作为“高保真 3D 副本”的可选“渲染插件”。对于社区中极少数追求顶级 3D 视觉的副本，可以设计一个接口，让 Unity 端的主神在加载该副本时，将渲染和交互委托给一个由 UE5 构建的独立场景或模块。结算清单仍然通过统一的接口回传。这既保全了 UE5 的视觉优势，又避免了让它承担它不擅长的框架核心职责。

### 💎 总结
选择 Unity，赌的是你项目“异构、快速、众创”的未来；选择 UE5，赌的是“单一副本的顶级视觉”。对于一个框架的启动阶段，前者的生存概率和迭代速度远高于后者。先用 Unity 把异构副本的切换和主神结算循环跑通，这比任何视觉保真度都更能验证你构想的核心可行性。

### 🎛️ DSH（DeepSeek Harness）：有专门的社区插件，开箱即用
针对 DSH 有一个专门的社区插件 dsh-unity-mcp，安装后就能让 DSH 里的 AI Agent 直接操控 Unity 编辑器。它本质上是对开源项目 mcp-unity 的封装，内置了服务端，零配置，无需手动编辑配置文件。
它提供了 34 个 Unity 工具，覆盖了游戏开发的关键环节：场景管理、GameObject 的增删改查、组件与材质操作、Prefab 管理、菜单执行、测试运行以及控制台日志读取等。Agent 内调用形式类似于 mcp__unity__create_scene、mcp__unity__update_gameobject。这个插件还包含连接诊断（先探测 Unity 网桥是否在线）和自动重连机制，对开发流程比较友好。

### ⌨️ Codex：Unity 官方插件，质量更有保障
Codex 这边是 Unity 官方直接维护的插件，定位是让 Codex 使用 Unity 工程师编写的“技能”来工作。它首先会检查你的项目，然后使用当前有效的 API，并在把结果交给你之前进行验证，这有助于规避通用 AI 模型常犯的“使用过时 API”的问题。-16
插件包含 31 个由 Unity 各功能团队维护的技能，覆盖 UI Toolkit/uGUI、2D 与 Tilemap、URP 与 Shader Graph、音频、导航与物理、多人游戏、Web 与本地化等。它还提供 unity-cli 技能，可以在终端中安装编辑器版本、创建和打开项目、管理软件包。设置只有两条命令或一键安装，兼容 Unity 6+。-16

### 🔌 如果你不想绑定特定 Agent：通用的 MCP 桥接
除了 DSH 和 Codex 的专用方案，还有多个通用的 Unity MCP 服务器，可以让 Claude、Cursor、VS Code Copilot、本地 LLM 等任何兼容 MCP 的客户端来控制 Unity。比较活跃的选择包括：
- CoplayDev/unity-mcp：提供约 50 个工具入口，支持从 Unity 2021.3 LTS 到 6.x，MIT 协议，免费。

- AnkleBreaker-Studio/unity-mcp-plugin：工具数量多达 268 个，覆盖场景、GameObject、组件、构建、性能分析、Shader Graph、地形、物理、NavMesh 等，同样是免费开源。

- sebastiankurvers-dev/agent-bridge-for-unity：提供 243 个 MCP 工具，包括场景搭建、视觉 QA、Play Mode 控制等。

Unity 官方的 MCP 服务器本身是包含在 AI Assistant 包中的，需要 Unity 6 及有效订阅才能使用。但上面这些社区方案大多不依赖官方订阅，兼容范围也更广，可以根据你的具体工具链偏好来选择。-1

### ⚠️ 能力边界与需要留意的点
Agent 能做的事情已经很深，但并非没有边界，有几个点值得在项目设计时留意：
第一，Unity 的服务条款对 AI 接入有框架性要求。 2026 年 6 月更新的 ToS 规定，AI agents、LLM 和 MCP 客户端/服务器只能通过 Unity 运营或指定的框架与平台交互。这意味着如果你的项目要长期维护，优先选择 Unity 官方认可的 MCP 路径（官方插件或官方 MCP 服务器）会更稳妥，社区 MCP 方案在合规上存在不确定性。
第二，Agent 的控制能力是“编辑器操作层”的，不是“游戏逻辑层”的。 它们可以创建场景、修改组件、编辑 C# 脚本、运行测试，但你的“主神结算逻辑”和“异构副本 schema”仍然需要由人类来设计和实现。Agent 擅长的是把已经想清楚的结构快速搭建出来，而不是替你决定这个结构应该长什么样。
第三，部分操作存在风险。 有分析指出，Unity MCP 工具中相当一部分具备修改或销毁数据的能力，一些破坏性工具没有内置限制。在你的众创项目中，如果让 Agent 直接对主神账本相关的场景或脚本进行操作，建议在 CI 或权限层面加入写操作限制，避免 Agent 在循环中意外触发批量修改。

### 📜 核心契约：用“公证”取代“统一”
《轮回乐园》里最值得借鉴的概念是公证体系。每个乐园（主神）都有一个专属的阵营烙印，它集任务接取、储物、契约签订于一体，是所有规则的物理载体。对于你的框架，这意味着副本不需要和主神共享一套属性，但它必须通过主神的“公证接口”才能被认可。-1
具体可以落成两条硬规则：
- 入场公证：副本加载时，主神只做三件事——校验副本声明的“属性轴”（如生存副本的健康/饥饿、战斗副本的力/敏/体/智）是否符合底层数据格式规范，确认副本引用的场景资产ID在库，并冻结轮回者进入时的状态快照。

- 产物公证：未经主神公证的物品或能力，只能在当前副本内使用，无法带出。这条规则直接堵死了副本作者通过私自定义超模道具来破坏跨副本平衡的可能——东西可以用，但想变成“永久资产”，必须走主神的结算通道。-22

### 💰 收益结算：主神拥有最终的“定价权”和“评级权”
你之前设想“副本收益按主神框架转换”，小说里给出了非常具体的操作范式。主神结算时不关心副本内部的经济系统，它只认几个抽象指标：
- 世界之源/战斗贡献：副本结束时，主神根据轮回者在副本内的行为（击杀、探索、任务完成度）统一折算为贡献值。贡献值可以按比例转化为主神空间的通用货币（如乐园币），例如《轮回乐园》中战斗贡献值0.1% = 乐园币50。

- 强制评级与晋升：主神会根据结算数据对轮回者进行世界结算评价（如S-、A级），并可能强制调整其权限等级。例如当检测到轮回者实力远超当前阶位上限时，乐园会强制提升其等级并开启晋升试炼，而不是任由其在低阶副本里“炸鱼”。

- 属性上限锁：主神对“裸装属性”设有硬性门槛（如任意裸装属性达到50点才满足某些晋升条件）。副本里可以给你临时buff，但永久属性点的投放权必须握在主神手里。

这意味着副本作者只需要在结算清单里填写“本次产出：战斗贡献X点、可公证物品ID列表”，换算汇率和稀有度映射完全由主神侧的配置文件决定。副本的自主性止步于产出申报。

### ⚖️ 越界惩罚：让“规则之内”具有威慑力
《轮回乐园》中轮回乐园的“惩罚措施在各大乐园中排名第一”，且对违规者有强制处决的权限。映射到你的框架，这对应的是对副本作者和轮回者（玩家）的双向约束：
- 对副本作者的约束：如果副本试图绕过公证接口直接写入主神账本，或者在副本内植入恶意脚本，主神应具备直接拒绝加载该副本或强制回滚的能力。副本的“自主性”必须运行在一个权限受限的沙盒中，它只能读取快照，不能触碰持久化存储。

- 对轮回者的约束：主神可以定义违规行为（如利用副本机制漏洞刷取收益），并设置从“收益清零”到“永久死亡标记”的阶梯惩罚。惩罚规则的执行者必须是主神引擎，而不是副本脚本。

### 🪜 权限分级：副本的“自主性”本身也分等级
你提到“新手关卡”和“高难副本”应有不同的规则强度，小说中的阶位体系可以直接借用。主神可以给副本设定权限上限：
- 低阶/新手副本：属性轴极简（如只有健康和饥饿），主神对副本内部规则的干预度最低，几乎完全放手。

- 高阶副本：副本可以拥有更复杂的内部规则（如完整的力敏体智系统），但结算时的校验项也更多、更严格。高阶副本的产物需要经过更严格的“公证”（如“完全公证”vs“自由公证”，后者属性部分保密但公证费更低）。-22

- 晋升试炼：当轮回者触发晋升条件时，主神可以指定一个特殊副本作为试炼场，该副本的结算规则由主神直接注入，副本作者无权修改。

### 💎 落到你的架构上
你不需要把《轮回乐园》的所有设定都搬进来，但“公证-结算-惩罚”这三件套构成了“自主性在副本，终裁权在主神”的最小闭环：
- 公证接口是副本获得“合法身份”的唯一入口；

- 结算清单是副本向主神“报税”的唯一通道，主神拥有汇率和评级的单方面定价权；

- 沙盒权限确保副本永远无法绕过接口直接篡改主神账本，越界即被拒绝或回滚。

这样，你的副本作者可以尽情折腾3D、2D、涂鸦风格和千奇百怪的内部属性，但只要他想让玩家把东西带出去，就必须跪在主神的规则面前。这正是乐园阵营那种“放养但可控”的精髓。

### 🏛️ 核心差异：单一的“神” vs. 可被博弈的“权力机构”
《轮回乐园》的乐园是一个近乎绝对的、人格化的规则化身，它的意志就是终裁。
而《无尽武装》的顶层是一个更复杂、甚至可以被渗透和对抗的政治实体。它的“主神”并非单一存在，而是“议会.主宰”的二元结构。具体来说，存在一个“最高议会”作为都市的掌控者，同时还有“主宰”这一势力。小说中甚至出现了“空间之子”这种拥有最高议会与主宰都无法拥有的权限的特殊存在。这意味着在《无尽武装》里，“主神”的规则不是不可质疑的铁律，而是一个充满漏洞、可以被研究、利用甚至篡改的系统。主角沈奕的核心行为之一，就是不断试探和利用主神空间的规则来谋取利益。-4
对你的框架而言：《轮回乐园》式的“主神”是一个不可违逆的终极规则制定者；而《无尽武装》式的“主神”更像一个可以被逆向工程和博弈的复杂制度。后者天然允许甚至鼓励“刁民”型玩家/副本作者去探索规则边界，这可能会带来更丰富的策略深度，但也对框架的鲁棒性提出了更高要求。

### 🌍 副本的“自主性”：功能相似，但驱动逻辑不同
在给予副本/任务世界自主空间这一点上，两者有功能上的相似性，但内在逻辑不同。
《无尽武装》创造性地引入了“血腥都市”与“荒野”的二元结构。-17
- 血腥都市：提供基础、有限但风险可控的稳定收益，类似于“主线副本”。

- 荒野：则完全相反，收益特殊且无上限，但风险难以估计，类似于高自由度的“开放世界”或“隐藏副本”。荒野中埋藏着历史的隐秘，提供独特的战略道具。

对你的框架而言：这提示你，副本的“自主性”可以不仅仅是风格上的（3D/2D），还可以是风险与回报结构上的分层。你可以设计“标准公证副本”和“未公证/荒野副本”两类通道，后者允许更高的收益和更离谱的规则，但主神不为其内部平衡性背书，结算时也会进行更严苛的审查或折价。

### 💀 结算与惩罚：相似的外壳，不同的内核
两者都使用硬通货和严厉的惩罚来驱动行为，但目的不同。
《无尽武装》的硬通货是“血腥点”。任务有明确的基准分，完成奖励点数，失败则扣除点数，点数不足者直接抹杀。小说中也体现了对通胀的严格控制，什么级别的强化对应什么级别的世界，收益都有估算。-17
这与《轮回乐园》的公证与惩罚机制在功能上高度对应：用统一的结算货币和死亡威胁来约束玩家，并维持经济系统的稳定。
关键区别在于“谁在制定价格”。《轮回乐园》的定价权归属于一个超然的规则意志。而《无尽武装》的定价体系存在于一个可以被“聪明人”利用漏洞的环境中。例如，主角曾利用规则，通过“拍电影让主神收录”来获取权限奖励进入副本刷分。这意味着它的结算规则本身就是一个博弈对象。

### 💎 对你的“主神框架”的启示
《无尽武装》为你提供了第二个设计锚点，让你可以在两种主神哲学之间做选择，或者进行混合：

设计维度 | 《轮回乐园》式（绝对规则化身） | 《无尽武装》式（可博弈的制度机构） |
主神本质 | 不可质疑的终裁者 | 有漏洞、可被研究/利用的复杂系统 |
规则刚性 | 高，规则即铁律 | 相对较低，规则是博弈的棋盘 |
玩家策略 | 在规则内寻求最优解 | 寻找规则漏洞，尝试“超越”或“利用”系统 |
副本自主性 | 通过“公证”接口进行受控的放权 | 通过“都市/荒野”的风险分层来实现 |
框架风险 | 较低，但可能抑制“刁民”创造力 | 较高，需要强大的反作弊和动态平衡能力 |

如果你的众创项目希望鼓励社区作者和玩家去钻研、试探甚至“玩弄”规则，那么《无尽武装》这种“权力机构”式的主神会提供更肥沃的土壤。但代价是，你的“主神”不能只是一个静态的结算接口，它必须是一个能够感知、分析并响应规则滥用的动态系统，这比实现一个单纯的“公证-结算”闭环要复杂得多。

===== [turn 15] USER =====
还有惊悚乐园和王牌进化还有无限恐怖,这些呢？

===== [turn 16] ASSISTANT =====
这三部作品恰好代表了无限流框架演化的三个关键岔路口：《无限恐怖》是必须理解的“原点”，《王牌进化》是“系统扩张”的范本，而《惊悚乐园》则提供了最激进的“元规则”视角。

### 📜 《无限恐怖》：原点与不可动摇的“硬约束”
作为开山之作，它确立了最基础也最强硬的主神范式，核心在于极简的闭环与绝对的约束力。它的主神是一个功能高度集中的黑箱，只负责三件事：发布强制任务、提供兑换强化、控制时空穿越。轮回者没有选择权，只能在“完成或抹杀”的二元规则下求生。-16
这对你框架的启示在于“惩罚的确定性”：奖励体系可以复杂（奖励点+支线剧情），但惩罚必须是简单、明确且由主神单方面强制执行的，比如点数耗尽即抹杀。基因锁的设定提供了一个重要的设计参照：它的突破只能在生死边缘的副本内触发，主神无法直接赋予，这暗示了你的框架可以设计一些只在副本内部才能获得、但结算后能被主神公证的“稀有成长路径”，以此激励玩家冒险，同时保持主神的最终裁决权。

### ⚙️ 《王牌进化》：从“黑箱”到“可运营的系统”
《王牌进化》的关键进化在于把主神空间从“中转站”扩张成了一个独立的“第三世界”。轮回者不再只是任务间隙匆匆兑换，而是可以在空间内交易、交流，形成工会。这意味着主神框架从纯粹的“任务发布器+商店”，变成了一个具备内部社会与经济系统的持久化平台。-7
它的“场景规则分层”机制尤其值得借鉴：副本被明确区分为“和平场景”“掠夺场景”“契约场景”等不同类型，不同场景适用完全不同的底层交互规则（如能否PVP、交易是否受保护）。这比你之前设想的按“视觉风格（3D/2D）”分层更进一步，它按玩家间的交互规则来定义副本性质。你的框架可以引入类似的“场景规则标签”，让副本作者在申报时选择，主神据此在结算时套用不同的公证与税率规则。-8
此外，它的“扭曲节点”概念（在遵循原作地理逻辑的世界中，植入如楼梯幻境、青铜巨门等规则化空间折叠）提供了一种在不破坏副本世界观自洽性的前提下，注入超规则机制的巧妙方法。你的副本作者可以借鉴此设计，在写实风格的副本中嵌入一个规则完全不同的“异常区域”，主神只需认可这个“异常区域”作为一个合法的结算单元即可。

### 🎭 《惊悚乐园》：最激进的参考——“真实性即规则”与“元游戏”
《惊悚乐园》与其他作品最大的不同在于，它本质上是一个虚拟现实游戏，甚至其存在本身就是一个由神魔设计的“赌斗场”。这赋予了它两个极其独特的机制。
第一，“真实性即规则”。副本世界严格遵循物理逻辑与叙事逻辑，玩家的行为会触发不可逆的世界反馈。例如，丧尸的肉可以作为体能补给，锻造出超越系统评级的神器会直接导致物品“品质溢出”。这意味着主神不再需要预先定义一切可能性。在你的框架中，如果允许副本内部存在一套自洽的物理/因果模拟，那么玩家基于这套逻辑产生的“预期外行为”（如利用场景特性达成目标），主神可以在结算时将其识别为合法的、甚至高价值的“技巧值”来源，而不是视为漏洞。-1
第二，它引入了“元规则”视角。惊悚乐园的主神之上还有“神魔赌局”的策划者，游戏内的管理员（GM）也拥有不同的权限层级。这对你“众创”框架的治理结构有直接启发：主神可以不是唯一的“神”。你可以设计一个分层的权限体系——顶层是框架维护者（定义公证汇率、惩罚阶梯等基础规则），中层是副本审核者（拥有加载/拒绝副本的权限），底层才是副本作者与玩家。这能让你在保持“主神终裁”的同时，将一部分治理责任下放，避免维护者成为唯一瓶颈。-1

### 💎 对你框架设计的整合启示

小说 | 核心贡献 | 在你的框架中可落地的机制 |
《无限恐怖》 | 硬约束与确定性惩罚 | 强制任务与抹杀规则由主神引擎单方面执行；设计仅在副本内触发的稀有成长路径（如基因锁），结算时由主神公证。 |
《王牌进化》 | 系统扩张与规则分层 | 将主神空间设计为可交易的持久化平台；引入场景规则标签（和平/掠夺/契约），主神据此差异化公证；允许副本内存在“扭曲节点”式的规则异常区。 |
《惊悚乐园》 | 真实性模拟与元治理 | 允许副本内部自洽的物理/因果模拟，预期外但合乎逻辑的行为可被结算为高价值产出；设计分层治理结构，区分框架维护者、副本审核者与内容创作者权限。 |

这三部作品共同指向一个结论：你的“主神”不必是一个全知全能、事无巨细的规则定义者。它可以是一个薄而坚硬的裁决层（《无限恐怖》的强制力），架设在一个可运营的持久化平台（《王牌进化》的空间）之上，并允许其下的副本世界拥有自洽的模拟深度（《惊悚乐园》的真实性），同时通过分层的治理权限（《惊悚乐园》的元规则）来管理众创带来的复杂性。这正好契合你“副本有自主性，但硬框架在主神之中”的核心构想。
